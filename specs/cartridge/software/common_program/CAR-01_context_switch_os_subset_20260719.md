## 1. 位置づけと読み方

本機構は、CH32V003（RV32EC・SRAM 2KB・内蔵Flash 16KB）という極小資源の上で、**複数のサブプログラムを呼び出し・復帰しながら実行する**ための仕組みである。OS のプロセス切り替え・動的リンク・メモリ管理に相当する機能を、**必要な部分だけ選択的に実装したサブセット**として捉えると全体像が掴みやすい。

読み方の順序:
- まず **§2 対応表**で全体像を掴む。
- **§3 メモリモデル**で図の読み方（Zone・セル・CTXスタック）を頭に入れる。
- **§4 動作の実例**で、3つの確認ケースについて**メモリマップがステップごとにどう変化するか**を追う。ここが本書の中核であり、抽象的な説明より先に具体例で動きを掴むことを意図している。
- 以降の §5〜§9 は各サブシステムの詳細、§10 はオーケストレータの置き方と「できる/できない」の境界、§11 は制約と不変条件。§4 で見た動きの裏付けとして参照する。

|---|---|---|
| コンテキストスイッチ | `iap_call` / `iap_return`（sp/ra/s0/s1/gp ＋ Zone C を退避・復元） | §5 |

**設計の一貫した原則**: SRAM も App Area も**呼び出し先のサイズに比例した可変長**で扱い、固定確保による無駄を避ける。ただし退避先の窓（Zone C 1024B・App Area 32セル）自体は固定で、その中で使う量を変える。

## 3. メモリモデル

図で使う3つの領域を先に定義する。以降の図はすべてこの表記に従う。

### 3.1 SRAM（2KB・0x20000000〜0x20000800）

```
0x20000000  ┌───────────────────────────────┐
            │ Zone A: System (common_prog)   │ 768B  機構の静的変数・g_restore_*
0x20000300  ├───────────────────────────────┤
            │ Zone B: オーケストレータ stack │ 256B  常駐オーケストレータ専用
0x20000400  ├───────────────────────────────┤
            │ Zone C: サブプログラム退避領域 │ 1024B ★実行中アプリのSRAMが載る窓
0x20000800  └───────────────────────────────┘ _eusrstack   gp=0x200007FC はこの窓を指す
```

- **Zone C が主役**。実行中のサブプログラムの SRAM（スタック・静的変数）は常に Zone C（0x20000400〜0x20000800）に載る。呼び出しの深さが変わっても Zone C のアドレスは動かない（単一ウィンドウ再利用）。
- コンテキストスイッチとは、実質「**Zone C の中身を FRAM に退避し、別のサブプログラムの SRAM を Zone C に載せる**」操作である。
- 退避するのは Zone C 全部ではなく、呼び出し先サイズに応じた `sram_size` バイトだけ（可変長）。

### 3.2 App Area（内蔵Flash 8KB・0x2000〜0x3FFF）

```
0x2000  cell0  cell1  cell2  cell3  ...  cell31        （256B × 32セル）
        ├──────┼──────┼──────┼──────┼─── ... ──┤
        │  各セル 256B。サブプログラムはセル境界に配置される               │
0x4000  └────────────────────────────────────────────┘
```

- サブプログラムのコードはここに**動的に配置**される。1セル=256B、全32セル。
- あるサブプログラムが何セル占有するかは `ceil(申告サイズ / 256)`。
- **セル N の実アドレス = 0x2000 + N × 256**。

### 3.3 FRAM CTX スタック（0x22000〜・16KB）

```
0x22000  ┌─ ヘッダ 16B ─────────────────────────┐
         │ status(1) fram_free(2) depth(1) top_ptr(4) 予備 │
0x22010  ├─ エントリ[0] ───────────────────────┤  ← CTX_STACK_ENTRY_BASE
         │ ヘッダ32B（sp/ra/s0/s1/gp/caller配置情報/sram_size…） │
         │ ＋ sram_data[sram_size]（Zone C退避分）              │
         │ ＋ フッタ2B（エントリ長）                            │
         ├─ エントリ[1] ───────────────────────┤  （LIFOで上へ伸長）
         │ ...                                                 │
         └──────────────────────────────────────┘
```

- コンテキストスイッチのたびに、呼び出し元の状態が**1エントリ**として LIFO で積まれる。
- 1エントリ長 = **34B（ヘッダ32B＋フッタ2B）＋ sram_size**。`sram_size = max(64, 占有セル数 × 32)`。
- `top_ptr` が次の書き込み位置、`depth` が現在の多重度（＝中断中サブプログラム数）。

### 3.4 SPI Flash（マスターイメージ）

- 各サブプログラムの**原本（未パッチ・0x2000基準）**は SPI Flash に常駐する。
- App Area へロードするたびに、この原本を読み出し → 配置セルに応じてパッチ（§7）→ 内蔵Flashへ書込。**マスターは常に未パッチのまま保つ**（再ロード・sticky 再ロードで何度でも読み直せる）。

## 4. 動作の実例：メモリマップの経時変化

ここが本書の中核である。3つの確認ケースについて、**各ステップでメモリマップ（App Area セル・Zone C・FRAM CTXスタック）がどう変化するか**を図で追う。図の凡例:

```
App Area:  [A A A .  .  ...]   A=アプリA占有セル / .=空きセル（左からcell0,1,2,…）
Zone C  :  ( A )               ( )の中身=いま Zone C に載っているサブプログラムのSRAM
CTXスタック: depth=N  [ 積まれているエントリを底→上で列挙 ]
実行中   :  ►X                  いま走っているサブプログラム
```

---

### ケースA：A-1 単純呼び出しと往復（最も基本）

アプリ **A**（申告768B＝3セル）が、モジュール **B**（申告256B＝1セル）を `iap_call` し、B が `iap_return` で戻る。

**Step 0 — 初期状態（A が実行中）**
```
App Area : [A A A .  .  ...  .]      cell0-2 = A
Zone C   : ( A のSRAM )              gp→Zone C
CTXスタック: depth=0  [ 空 ]
実行中    : ►A
```

**Step 1 — A が `iap_call(B)` を発行 → 機構が A を退避**
```
処理: ① A の sp/ra/s0/s1/gp と Zone C(sram_size=96B) を CTXスタックへ push
      ② allocate(1) が空きセル cell3 を選定 → B をマスターから読み出し・パッチ・書込
      ③ B のエントリポイントへジャンプ

App Area : [A A A B .  ...  .]      cell0-2=A(中断), cell3=B
Zone C   : ( B のSRAM )              ← Zone C の中身が A→B に入れ替わった
CTXスタック: depth=1  [ 底: A(sram=96,復帰先cell0) ]
実行中    : ►B
```
> ポイント: A のコードは App Area に**残ったまま**（cell0-2）だが、SRAM だけが B のものに切り替わる。A の生きた変数は CTXスタックに退避されている。

**Step 2 — B が `iap_return` を発行 → 機構が A を復元**
```
処理: ① CTXスタックから A のエントリを pop → Zone C へ sram_data(96B) を復元
      ② A の sp/ra/s0/s1/gp を復元
      ③ A の復帰先（cell0 のエントリポイント直後）へジャンプ

App Area : [A A A B .  ...  .]      cell3=B は残置（次回呼べばヒット）
Zone C   : ( A のSRAM )              ← Zone C が A に戻った
CTXスタック: depth=0  [ 空 ]
実行中    : ►A（iap_call の次の行から継続）
```
> ポイント: `iap_return` は B のセルを**消さない**。B は配置状態表に在席したまま残り、次に A が B を呼べば**ロード不要（ヒット）**で即ジャンプできる。セルが消えるのは、後で別モジュールの配置でそのセルが選ばれて追い出される（evict）ときだけ（§6）。

---

### ケースB：多重ネスト（3段）

A → B → C と入れ子に呼び、C→B→A と LIFO で戻る。CTXスタックが伸縮する様子を見る。（B=2セル・C=2セル と仮定）

**Step 0**
```
App Area : [A A A .  .  .  ...]     A=cell0-2
CTXスタック: depth=0  [ 空 ]        ►A
```

**Step 1 — A が B を call**
```
App Area : [A A A B B .  ...]       B=cell3-4
CTXスタック: depth=1  [ A ]          ►B
Zone C   : ( B )
```

**Step 2 — B が C を call**
```
App Area : [A A A B B C C ...]      C=cell5-6
CTXスタック: depth=2  [ A , B ]      ►C     ← 底からA,B の順に積まれている
Zone C   : ( C )
```

**Step 3 — C が return（→ B へ）**
```
CTXスタック: depth=1  [ A ]          ►B     ← B のエントリを pop・Zone C を B に復元
Zone C   : ( B )
App Area : [A A A B B C C ...]      C は残置
```

**Step 4 — B が return（→ A へ）**
```
CTXスタック: depth=0  [ 空 ]         ►A     ← A のエントリを pop・Zone C を A に復元
Zone C   : ( A )
App Area : [A A A B B C C ...]      B,C とも残置（追い出されるまで在席）
```
> ポイント: 復帰は必ず **LIFO（積んだ逆順）**。`depth`（多重度）が中断中サブプログラム数を数えており、`top_ptr` がスタック末尾を追う。App Area にはこの例では A(3)+B(2)+C(2)=7セルが同時在席し、32セルに十分収まる。

---

### ケースC：App Area 溢れ → LRU 追い出し → sticky 再ロード

ネストが深くなり **必要セル数が32を超える**と、アロケータは既存モジュールを**追い出して**場所を作る。そして復帰時、追い出された呼び出し元は**元と同じセルへ再ロード**（sticky）される。この振る舞いが本機構のメモリ管理の核心である。（実試験 IT-IAP-05＝多重度15・33セルを縮約して図示）

前提: L0（3セル）＋モジュール（各2セル）を積んでいくと、モジュール15個目で 3+2×15=33セル > 32セル となり溢れる。溢れる瞬間だけを抜き出す。

**Step n — 溢れる直前（31セル使用・空き1セル）**
```
App Area : [L0 L0 L0 m1 m1 m2 m2 ... m14 m14 .]   使用31 / 空き1（cell31）
CTXスタック: depth=14  [ L0, m1, ..., m14 ]        ►m14
LRU seq  : L0 が最小（最初に中断して以来ずっと最古）
```

**Step n+1 — m14 が m15 を call → 2セル要るが空きは1セル → 追い出し発生**
```
処理: ① allocate(2) の窓探索：空き2連続が無い → コスト最小（LRU最古）の窓を選ぶ
      ② LRU 最古の L0（cell0-2）が追い出し対象。L0 の3セルを空けて m15 を配置
         （※窓は連続2セル。L0の3セルのうち先頭2セルが m15 に使われ、残り1セル＋既存空き1で調整）

App Area : [m15 m15 . m1 m1 ... m14 m14 .]        L0 が消え、m15 が入った
CTXスタック: depth=15  [ L0, m1, ..., m15 ]        ►m15
        ★L0 は「中断エントリ」としてCTXスタックには残っている（コードだけ追い出された）
```
> ポイント: **L0 のコードは App Area から消えたが、L0 の SRAM スナップショットと復帰先セル番号（cell0）は CTXスタックのエントリに保持されている**。だから復帰は可能。

**Step n+2 — m15 が return → L0 が sticky 再ロードされる**
```
処理: ① m15 のエントリを pop → 復帰先は L0
      ② L0 が App Area に不在と判明 → sticky 再ロード発動:
         L0 のマスターを読み、記録済みの復帰先 cell0 へ delta=0 でパッチ・書込
      ③ この再配置(3セル)が今度は最古の別モジュール(m15の残骸)を追い出す
      ④ Zone C を L0 のスナップショットで復元し、L0 の復帰先へジャンプ

App Area : [L0 L0 L0 m1 m1 ... .  .]              L0 が元のcell0-2 へ戻った
CTXスタック: depth=14  [ L0(→復帰済), m1, ..., m14 ] ►L0
Zone C   : ( L0 )
```
> ポイント（sticky の要）: 通常ロードは**空いている好きなセル**に置けるが、**復帰のための再ロードは必ず元と同じセル（cell0）**でなければならない。なぜなら L0 のスナップショット（と、まだ復帰していない祖先のスナップショット）は「L0 は cell0 にいる」前提でパッチされているから。この「復帰先セル固定」を **sticky 配置**と呼ぶ。
>
> **開発者規約との接点（§12・規約3）**: sticky 再ロードは L0 のマスターを読み直してパッチし直す。このとき `find_resource(PATCH|L0)` が引けないと**無言でハングする**。本体（L0）は通常 cell0・delta=0 で動くためパッチテーブルを必要としないが、**この追い出し→再ロードの瞬間にだけ要求される**。したがって「App Area を使い切る可能性のあるアプリは本体にもパッチテーブルを登録する」ことが規約になっている。

## 5. コンテキストスイッチ

`iap_call` / `iap_return`（パターンA）は、呼び出し元の**実行文脈**を保存・復元する。

**退避・復元する対象**:
- レジスタ: `sp`（スタックポインタ）・`ra`（戻りアドレス）・`s0`・`s1`（callee-saved）・`gp`（グローバルポインタ）
- SRAM: Zone C の `sram_size` バイト（呼び出し元サイズに比例した可変長）

**退避先**: FRAM CTXスタックの1エントリ（§3.3）。ヘッダ32B にレジスタと配置情報、続いて sram_data、末尾にフッタ2B。

**gp を退避対象に含める理由**: サブプログラムはサイズクラスごとに `__global_pointer$` が異なり得るため、復帰時に gp を戻さないと呼び出し元の gp 相対アクセス（8B以下の静的変数）が壊れる。→ 現在は gp を ABI 固定値 0x200007FC に統一（§8）することで根本解決しているが、退避・復元は防御層として維持している。

**所要時間**: 約117〜290ms。支配的なのは SRAM 退避ではなく**内蔵Flash（App Area）の消去・書込**（全体の約9割）。このため SRAM 側だけでなく App Area 側も可変長化している。頻繁な呼び出し（FEP 等）には不向きで、場面転換など「イベント」用途が適切。

## 6. メモリ管理

App Area 32セルへのサブプログラム配置を管理する。

- **配置状態表**: いまどのセルにどのサブプログラム（`(catalog_idx, res_id)` の組がキー）が在席しているかの表。各領域に `lru_seq`（16bit 単調増加）を持つ。
- **アロケータ `allocate(size_cells)`**: `size_cells` 連続セルの窓を探す。全空きの窓があれば即決。無ければ**各候補窓の占有領域の最新 seq をコストとし、最小コスト（＝最も古い＝次に使われるのが最も遠い）の窓**を選んで追い出す。
- **LRU の更新点**: ①ロード時 ②呼び出しヒット時 ③中断（suspend）時、に seq を刻む。呼び出しチェーン上では「中断順と復帰順が鏡像」であるため、LRU が経験則でなく**定理として Belady 最適に一致**する（詳細は設計書 §3.5.2.1）。
- **sticky 再ロード**: 中断中サブプログラムの復帰時は、記録済みの `start_cell` へ**必ず同じ配置で**再ロードする（ケースC 参照）。

## 7. 動的リンク

実行時リンクを、極小資源向けに**設計時固定＋静的リロケーション**で代替する。

- **RC_API 固定テーブル（0x08A0）**: 共通プログラム（1層）の機能はすべて固定アドレスのテーブル経由で呼ぶ。実行時シンボル解決を、設計時に固定したテーブルで置き換える。
- **パッチ機構**: サブプログラムを任意セルに配置するとアドレスが変わる。マスター（0x2000基準・未パッチ）を読み、配置先セルに応じた delta で該当箇所（PC相対で解決できない絶対参照など）を**書き換えてから**内蔵Flashへ書く。書き換え位置は PC側ツールが生成する**パッチテーブル**（リソース種別 0xE（★2026-08-14 に 0x6 から移動））に列挙される。マスターは常に未パッチのまま保つため、何度でも再ロードできる。

---

## 8. ABI規約

サブプログラムと機構の間の契約。詳細な開発者向けの遵守事項は §12・`CAR-01_app_dev_guide` §6 を参照。

- **gp 固定値 0x200007FC**: 全サブプログラムの `__global_pointer$` を絶対値 0x200007FC に統一（ld の SECTIONS 外で定義）。これにより機構の gp 相対静的変数アクセスがサイズクラスに依らず一定になる（`gp_abi_design.md`）。
- **引数/戻り値エリア**: FRAM 管理領域の4定数（A-1/A-2 の引数・戻り値、各256B・0x1A900〜0x1ACFF）。**メタ領域はキャッシュであり書き込み先ではない**（A-2 で再ロードされ消える）。
- **レジスタ保存契約**: 機構が sp/ra/s0/s1/gp を保存・復元（§5）。
- **SP固定**: Flash 書き換えフェーズでは SP を `_eusrstack`（Zone C 最上端）へ付け替え、スクラッチが Zone A/B に到達しないことを構造的に保証する。

## 9. 呼び出し種別（A-1 / A-2）

| 種別 | 意味 | メタ入替 | 用途 |
|---|---|---|---|
| **A-1（INTERNAL）** | 自アプリ内の別モジュール呼び出し | なし | 大規模アプリのモジュール分割 |
| **A-2（EXTERNAL）** | 別アプリ（公開サービス）呼び出し | あり（呼び出し先／復帰時にメタ8KBを再ロード） | 日本語入力 Wnn 等の公開サービス |

- **A-2 はステートレス規約**: A-2 はメタ領域を再ロードするため、呼び出し間で状態を保持できない。引数・戻り値は必ず FRAM 管理領域の A-2 定数（0x1AB00/0x1AC00）で受け渡す。
- A-2 呼び出しでは、呼び出し先アプリのリソースディレクトリを引くために、そのアプリのメタ8KBを FRAM_META_BASE へ Flash 原本から転送する（復帰時は呼び出し元のメタを戻す）。

## 10. オーケストレータの置き方と、できること・できないこと

複数のサブプログラムを呼び分ける「オーケストレータ（司令塔）」をどこに置くか、そして本機構で**できること・できないこと**を、開発者目線で整理する。

### 10.1 オーケストレータの置き場所（2択）

| 置き場所 | 追い出しの有無 | 使い方・注意 |
|---|---|---|
| **(a) 共通プログラム領域（常駐・非スイッチ）** | 追い出されない | 機構標準の「共通の呼び出し機構」はこちら。App Area の空き状況に依らず常に在席し、いつでも呼べる。将来の擬似マルチタスクの司令塔もここに置く想定。 |
| **(b) アプリ領域に L0 として置く** | **追い出され得る** | アプリが自前の司令塔モジュールを持つ場合。App Area が溢れると L0（＝オーケストレータ）自身も追い出し対象になる。 |

### 10.2 (b) で L0（オーケストレータ）が追い出されても壊れないようにする

(b) を選ぶ場合、L0 は App Area 溢れ時に追い出され、復帰時に **sticky 再ロード**で元のセルへ戻る（§4 ケースC）。これが正しく効くための**唯一の要件**は:

- **L0（アプリ本体）に PATCH テーブルを登録すること**（§12 規約3）。sticky 再ロードは L0 のマスターを読み直してパッチし直すため、`find_resource(PATCH|L0)` が引けないと**無言でハングする**。PC側カタログツールがこれを検査する（§12・`CAR-01_app_dev_guide` §6）。

> ※現状、特定サブプログラムを「**追い出し禁止（pin）**」にする機構は**提供していない**。L0 も含め全て「追い出され得る／sticky で正しく戻る」前提で設計する。pin はアロケータへの保護追加＝common_prog の Flash 消費を伴うため、要件が固まってから検討する。

### 10.3 できること・できないこと（境界）

本機構は**厳密な LIFO（後入れ先出し）の call / return スタック**である。

**できる:**
- **任意の深さのネスト呼び出し**（A→B→C→D→…）。
- **App Area（32セル）が溢れたら祖先を追い出し**、復帰時に **sticky 再ロード**で正しく元のセルへ戻す。多重に追い出されても LIFO で順に巻き戻る（例: D をロードするため B・C がまとめて追い出されても、D が `iap_return` すれば C→B→A と順に復元される。IT-IAP-05 で 15多重・33セル>32 を実証）。

**できない（設計スコープ外）:**
- **順不同の再開（コルーチン的な任意ジャンプ）**。D の実行中に「中断中の C を再開する」ことはできない。`iap_call(C)` は**新しい C インスタンスの配置**であって、中断中 C の再開ではない。中断中 C へ戻る唯一の方法は **D が `iap_return` すること**。
- したがって「呼び出しチェーンを外れて任意のサブプログラムへ飛ぶ」用途には使えない。必要なら、司令塔（オーケストレータ）が LIFO の枠内で呼び分ける設計にする。

### 10.4 PC側ガードレールと「意識しなくてよい範囲」

上記の制約（申告サイズ≥実体・本体PATCH登録・gp固定・LIFO）は、多くが **PC側カタログ生成ツールがビルド時に検査・保証**する（§12・`CAR-01_app_dev_guide` §6/§10）。したがって、標準の呼び出し機構を使う限り、開発者はメモリ配置や追い出しの詳細を深く理解しなくても**安全に実行できる**。本章は「自前の司令塔を持つ」「App Area を使い切る」など標準から外れた設計をする場合に、できる/できないの境界を把握するためのものである。

## 11. 制約と不変条件

- **App Area 上限 = 32セル（8KB）**。同時在席サブプログラムの合計セル数がこれを超えると追い出し（§6・ケースC）。
- **Zone C 上限 = 1024B**。`callee_sram_size` / `caller_sram_size` が 1024B を超える申告は `ERR_SRAM_FULL` で弾かれる。
- **段数律速は FRAM ではなく App Area のセル数**。CTXスタックは1エントリ最小98Bで理論上100段超入るが、実際は App Area 32セルが先に律速する。
- **【不変条件】窓探索は size_cells ≤ 32 を前提とする**: `ZONE_C_SIZE / calc_sram_sizeのセル係数 = 1024 / 32 = 32 = APP_CELL_COUNT`。上流の SRAM チェックが「32セル超＝sram_size>1024」を先に弾くことで、アロケータが候補窓0個でハングする経路に到達しない。`ZONE_C_SIZE`・セル係数・`APP_CELL_COUNT` のいずれかを変える際は不変条件 `ZONE_C_SIZE / セル係数 ≤ APP_CELL_COUNT` を必ず再確認する（設計書 §3.5.2.2）。

## 12. 開発者規約への索引

パターンA を使うアプリが守るべき5規約（詳細は `CAR-01_app_dev_guide` §6）:

1. 申告サイズ ≥ 実バイナリサイズ（PC側ツールが保証・検査）
2. A-2 公開サービスはステートレス（§9）
3. App Area を使い切る可能性のあるアプリは本体にもパッチテーブルを登録（ケースC・sticky 再ロード時のハング回避）
4. 引数・戻り値は FRAM 管理領域の4定数を使う。メタ領域には書かない（§8）
5. ld の `__global_pointer$` = 0x200007FC（§8・テンプレート ld で自動達成）

## 13. 用語集

| 用語 | 意味 |
|---|---|
| **Zone A / B / C** | SRAM 2KB の区画。A=機構の静的領域(768B)・B=オーケストレータstack(256B)・C=サブプログラム退避窓(1024B)。 |
| **セル（cell）** | App Area を256B単位で区切った枠。全32セル。サブプログラムはセル境界に配置される。 |
| **多重度（depth）** | 同時に中断しているサブプログラムの数。コールスタックの深さと一致するが、数えているのは「中断中サブプログラム数」。 |
| **sticky 配置** | 中断したサブプログラムの復帰時は、必ず元と同じセルへ再ロードする規則。スナップショットが配置前提でパッチされているため。 |
| **LRU seq** | 各在席領域が持つ単調増加カウンタ。ロード／ヒット／中断時に更新。追い出し犠牲者の選定に使う。 |
| **マスターイメージ** | SPI Flash 上の未パッチ・0x2000基準の原本。ロードのたびに読み直してパッチする。 |
| **パッチテーブル** | 配置セルに応じて書き換える箇所の一覧（リソース種別0xE（★2026-08-14 に 0x6 から移動））。PC側ツールが生成。 |
| **A-1 / A-2** | 呼び出し種別。A-1=自アプリ内（メタ入替なし）、A-2=別アプリ間（メタ入替あり・ステートレス）。 |
