## 1. 拡張コネクタ経由のコミュニケーション

### 1.1 背景・仕様書上の定義

cartridge_master_20260617.md §1.7 に 3 種の通信モードが定義されている。

| モード | プロトコル | 用途 | 推奨度 |
|---|---|---|---|
| Mode 1: スレーブ | **I2C スレーブ** | キーボードからのコマンド受信・状態通知 | 推奨 |
| Mode 1: スレーブ | UART 受信 | キーボードからの大量データ受信 | 可 |
| Mode 1: スレーブ | SPI スレーブ | タイミング制約が厳しく原則避ける | △ |
| Mode 2: マスター | I2C マスター / SPI マスター / UART TX | センサー・外部デバイス操作 | **実装済み** |
| Mode 3: バディ | **UART 3Mbps + DMA** | アプリ・データ転送（最大 800KB / 約 2.8 秒） | 推奨 |

### 1.2 現在の実装状況

**実装済み（Mode 2 のみ）:**
- `keyscan.c`: I2C マスター（AVR64DD28 からジョイスティック Read）
- `spi_manager.c`: SPI マスター（SPI Flash / FRAM / TFT / YMF825 CS 切り替え）

**未実装:**
- Mode 1（I2C スレーブ）: キーボード等からのコマンド受信インフラ
- Mode 3（UART 3Mbps + DMA）: アプリ・データの高速双方向転送

### 1.3 論点（打ち返し用）

1. **Mode 1・3 は common_prog（1層）が基盤を提供するか、アプリ（3層）任せにするか**
   - 1 層提供ならば RcApi テーブルへの追加が必要（ABI 固定のため末尾追加が必須）
   - 3 層任せならば HAL 不使用制約の中で各アプリが UART/I2C 初期化を独自実装

2. **Mode 3（UART DMA）をアプリが使う場合の DMA チャンネル競合**: SPI（DMA Ch2/3）との共存設計が必要

3. **キーボード接続を前提とするアプリ向けの公式サポート範囲**: 現行仕様では「拡張コネクタ通信を使うアプリはアプリ組み込み」と位置づけられているが、汎用化の余地はあるか

## 2. 各基板の MCU との通信

### 2.1 関連基板と通信経路

| 基板 | MCU | 通信方式 | 役割 |
|---|---|---|---|
| A基板 | ATtiny404 | I2C スレーブ（UIAPduino マスター） | 電源管理・CART_READY 出力・バッテリー残量通知 |
| B基板 | （MCU 変更検討中） | SPI スレーブ | FM 音源（YMF825）制御 |
| D基板 | （MCU 変更検討中） | I2C スレーブ | ジョイスティック・OLED・日本語入力 UI |

> **注記**: B基板・D基板の MCU は現在変更を検討中。仕様確定後に整合確認が必要。

### 2.2 現在の実装と spec との差異

#### AVR64DD28（D基板）I2C 通信

| 機能 | 実装状況 | 備考 |
|---|---|---|
| ジョイスティック Read（RAW 1B） | **実装済み**（keyscan.c） | 通常動作 |
| 日本語入力モード開始/終了 Write | **未実装** | UIAPduino → AVR64DD28 へ I2C Write |
| SYS_CMD 受信（音量変更・メニュー開閉） | **未実装** | AVR64DD28 → UIAPduino へ bit7=1 バイト |
| バッテリー残量 Write（残量値転送） | **未実装** | UIAPduino → AVR64DD28 へ I2C Write |

#### ATtiny404（A基板）I2C 通信

| 機能 | 実装状況 | 備考 |
|---|---|---|
| CART_READY HIGH 出力 | **実装済み（差異あり）** | spec: ATtiny404 I2C Write 経由 → ATtiny404 PA1 出力。実装: boot.c が CH32V003 GPIO（PA1）を直接出力している |
| バッテリー残量 Read（定期ポーリング） | **未実装** | UIAPduino → ATtiny404 Read → 残量値 1B 取得 |

#### YMF825（B基板）SPI 通信

- 現行設計では YMF825 の初期化・音色設定はアプリ（3層）組み込み（〜1KB 目安）
- common_prog は SPI バスの CS 管理（`spi_cs_select(SPI_DEV_YMF825)`）のみ担当
- **ただし B基板 MCU 変更により SPI→UART 等の通信方式が変わる可能性あり**

### 2.3 論点（打ち返し用）

1. **CART_READY の経路**: CH32V003 直接 GPIO 出力（現行）vs ATtiny404 I2C 経由（仕様書）どちらが最終実装か。ハードウェア配線によって変わるため確認が必要

2. **keyscan.c の責務拡大方針**: 現状は Read のみ。Write（モード通知・バッテリー転送）や SYS_CMD 受信を同一モジュールに追加するか別モジュール（`i2c_comms.c` 等）に分離するか

3. **SYS_CMD ハンドリングのタイミング**: boot_main() のアプリ選択 UI ループ中にも AVR64DD28 から SYS_CMD（音量変更等）が届きうるが、現行は無視。対応するか

4. **バッテリー残量ポーリング周期と実装箇所**: 定期ポーリングをどこで実行するか（タイマー割り込み？メインループ内？）

## 3. 各基板のファームウェアアップデート（必須・未実装）

### 3.1 ハードウェア設計（確定済み）

cartridge_master_20260617.md §2.5 に LOCAL_UPDI 機構が定義されている。

| ピン | UPDI 対象 | 更新中の制約 |
|---|---|---|
| PD0（BUSY_EINK / GPIO4_CS と兼用） | **AVR64DD28（D基板）** PA0 | FM 音源（YMF825）を停止すること ← **要再確認**（下記） |
| PD6（**CH32V303 UART_RX** と兼用） | **ATtiny404（A基板）** PA0 | e-ink 描画コマンドを送らないこと ＋ **B基板との UART 通信を停止すること**（下記） |

> ⚠ **2026-07-22 追記: 新B基板採用により PD6 の兼用先が変わり、更新中の制約が実質的に増えた。**
>
> PD6 は旧 B基板では `IRQ_N`（YMF825 割り込み）との兼用だったが、新B基板（YMF825×2 + CH32V303）では
> YMF825 が CH32V303 配下へ移管され IRQ_N が UIAPduino に届かなくなったため、**CH32V303 との常時 UART_RX**
> へ用途変更された（`cartridge_master` Rev.1.9 §2.5 / `cartridge_master_diff_20260703.md` で確定済み）。
> `LOCAL_UPDI_A`（A基板 ATtiny404 更新）との兼用は従来どおり維持される。
>
> **結果として、A基板の FW 更新中は B基板からの UART 受信が物理的に不可能になる。** 旧版の制約
> （e-ink 描画コマンドを送らないこと）に加え、**音源制御コマンドの送信停止・演算オフロードの停止**が必要。
> 更新中に .xm 再生や毎フレームのレイキャスティング要求が走っていると破綻する。
> 実装時は「A基板 UPDI 更新の前後で B基板通信を明示的に停止・再開する」手順を必須とすること。
>
> **PD0 側（D基板更新）の制約は要再確認。** 「FM 音源（YMF825）を停止すること」は YMF825 が UIAPduino の
> SPI 配下にあった旧構成に由来する。新B基板では YMF825 は CH32V303 配下のため、UIAPduino 側の直接的な
> 制約は消える可能性がある（`GPIO4_CS` が何を指すかを含め、`cartridge_master` §2.5 と突き合わせて確定すること）。
>
> あわせて、D基板 MCU が **ATtiny1604 → AVR64DD28** に変更されたため UPDI のページサイズ等が変わる
> （Q-7 の範囲）。本節の他の記述（§2.1 の「B基板＝SPI スレーブ」等）も新B基板＝UART 前提へ読み替えること。

### 3.2 UPDI プロトコルの概要

UPDI（Unified Program and Debug Interface）は Microchip/WCH が採用する 1-Wire 半二重シリアルプロトコル。CH32V003 側でソフトウェア bit-bang 実装が必要。

**主要なシーケンス（ATtiny 書き込み時）:**
1. UPDI 有効化: ブレーク信号 → SYNCH バイト（0x55）
2. NVM コントローラ解錠: Key コマンド発行
3. Flash 消去 → ページ単位書き込み（AVR64DD28: 64B ページ）
4. ベリファイ（オプション）
5. UPDI リセット → 新 FW 起動

### 3.3 実装方針（未決定・議論要）

**更新 FW バイナリの格納場所（案）:**
- SPI Flash システム予約ブロック内（§5.6 ブートローダアップデートと同一方式）
- 更新時に PC から外部通信モード経由で SPI Flash に書き込む

**更新トリガーの候補:**
- A案: boot_main() 起動時の特殊キー組み合わせ（例: 左右キー同時押し）
- B案: システムメニューから「基板 FW アップデート」を選択
- C案: 外部通信モード（GPIO2=HIGH）のサブコマンドとして PC から指示

**実装場所の候補:**
- A案: `local_updi.c` として common_prog に組み込む（常時 Flash に存在）
- B案: 更新プログラム自体を SPI Flash に格納し、§5.6 と同様に App Area IAP で実行（Flash 節約）

### 3.4 論点（打ち返し用）

1. **トリガーはどのパターンか**（上記 A/B/C 案）
2. **実装場所**: common_prog 組み込み vs App Area IAP 実行
3. **対象 MCU の UPDI アドレス・ページサイズ**: B基板・D基板の MCU 変更後に確定
4. **更新失敗時のリカバリ**: 途中失敗で ATtiny が文鎮化した場合の対処（外部 UPDI ライター必要？）

## 4. D基板連携 日本語変換機能（common_prog 側モジュール）

### 4.1 全体アーキテクチャ（仕様書既存）

```
呼び出し元アプリ（App Area 8KB）
  ↓ FRAM A-2 引数エリア（FRAM_IAP_A2_ARG = 0x1AB00・256B）にひらがな文字列を書く
  ↓ iap_call(callee_res_id, catalog_idx)  ← Wnn を SPI Flash から App Area にロード（約 110ms）

Wnn ブロック（2層 IAP ブロック・最大 4KB 枠）
  ↓ SPI Flash 辞書引き（乗算 1 発でアドレス計算）
  ↓ Viterbi 計算（単純変換はスキップ可）
  ↓ FRAM A-2 戻り値エリア（FRAM_IAP_A2_RET = 0x1AC00・256B）に候補フォント index 列を書き込む
  ↓ iap_return()  ← FRAM から SRAM イメージ復元のみ（約 0.7ms）

呼び出し元アプリ ← FRAM から確定文字列を読んで画面表示
AVR64DD28 ← I2C 経由で Wnn 起動前に「日本語入力モード開始」通知を受け取り OLED に候補表示
```

### 4.2 common_prog 側に必要な追加実装

| 機能 | 現状 | 必要な実装 |
|---|---|---|
| 日本語入力モード開始/終了通知 | **未実装** | `keyscan_set_mode(uint8_t mode)` 相当の I2C Write |
| Wnn エンジン本体 | 2層 IAP ブロック（SPI Flash 格納） | common_prog には入らない。アプリが iap_call() で呼び出す |
| FRAM 引数/戻り値エリア | **既設計・2026-07-17に配置を是正**（§5.4 の IAP A-2 引数/戻り値エリア `FRAM_IAP_A2_ARG`=0x1AB00 / `FRAM_IAP_A2_RET`=0x1AC00・各256B） | 追加実装は不要（機構はこの領域を参照しない）。**ただし旧配置（メタ情報領域内 0x16700/0x16740）を前提にしたコードを書かないこと**（下記） |
| AVR64DD28 からの候補確定 index 受信 | **未実装** | 確定 index は AVR64DD28 → UIAPduino I2C Write（SYS_CMD の拡張または専用コマンド） |

> ⚠ **2026-07-17: A-2引数エリアの配置を是正した（実バグ修正）。Wnn 実装前に必読。**
>
> 本節は当初「引数/戻り値エリアは設計済み・実装済み」としていたが、**旧配置（メタ情報領域内の 0x16700/0x16740）では A-2 の引数受け渡しが原理的に成立していなかった**。A-2 では共通プログラムが、呼び出し時に呼び出し先（Wnn）のメタ8KBを、復帰時に呼び出し元アプリのメタ8KBを、それぞれ **Flash 原本から再転送する**（呼び出し先のリソースディレクトリを引くために必要で、A-2 に本質的な動作）。旧引数エリアはこの8KBの内側にあったため、**呼び出し元が書いたひらがな文字列は Wnn が読む前に機構自身が塗り潰し**、Wnn が書いた候補 index 列も復帰時のメタ書き戻しで失われていた。
>
> **この不具合は A-2 呼び出し自体は成功する（status=0）ため、「呼び出しは通るのに変換結果だけが化ける」という形で現れる。** 2026-07-17 に4領域とも FRAM 管理領域へ移設して解消済み（`cartridge_master` §1.8・`CAR-01_common_program_spec` §5.4 Rev.0.5・`CAR-01_app_dev_guide`）。IT-IAP-04 で往復を実証しており、旧配置へ戻すネガティブコントロールで上記の壊れ方を再現している。
>
> 規約: 引数は `iap_call()` の直前に書き、Wnn は入場直後に読む。Wnn は `iap_return()` の直前に戻り値を書く。**メタ情報領域はアプリが書き込む場所ではない**（A-2 のたびに Flash 原本から再ロードされる）。

### 4.3 論点（打ち返し用）

1. **モード通知コマンドのバイトフォーマット**: D基板 FW 仕様書（boards_D_board_firmware_20260809.md §3）では Write（モード通知）のバイト値が未定義。確定が必要

2. **候補確定 index の受信路**: AVR64DD28 → UIAPduino への返送を SYS_CMD の一種とするか、別コマンドバイトとするか

3. **D基板 MCU 変更の影響**: AVR64DD28 → 別 MCU に変更された場合、I2C アドレス・コマンド体系が変わる可能性がある

## 5. 起動シーケンス 各パターンのウォークスルーと欠落要素確認

### 5.1 Pattern 1: 通常起動（App Area にアプリあり）

```
UIAPduino ブートローダ
  → boot_main()（common_prog）
  → IWDG 初期化（WDT 有効化）
  → keyscan_init()（I2C + AVR64DD28 初期化）
  → ボタン状態確認（未押下）
  → App Area 有効チェック
  → 恵梨沙フォント転送（SPI Flash 0x008000 → FRAM 作業領域・約 18ms）
  → CART_READY HIGH（※）
  → App Area（0x1E00）に制御移転
```

**欠落候補・確認事項:**
- **(※) CART_READY のタイミングと経路**: フォントロード後 vs 前。CH32V003 直接 GPIO vs ATtiny404 I2C 経由
- **バッテリー残量の初回取得・AVR64DD28 への転送**: どのタイミングで行うか未定義
- **App Area 移転後の WDT キック**: アプリ側が WDT キックを忘れるとリセットがかかる。ガイドライン化が必要

### 5.2 Pattern 2: アプリ選択（決定ボタン押下・GPIO2=LOW）

```
boot_main()
  → 決定ボタン押下を検知
  → 200ms 待機（キーボード側 GPIO2 セットアップ猶予）
  → GPIO2=LOW 確認
  → FRAM からアプリ一覧取得（キャッシュ）
  → TFT / e-ink にアプリタイトルリスト表示
  → 上下キーで選択・決定キーで確定
  → IAP 書き込み（SPI Flash 選択ブロック → App Area 8KB）
  → メタ情報（6KB）を FRAM 作業領域に転送
  → ソフトウェアリセット → Pattern 1 へ
```

**欠落候補・確認事項:**
- **選択 UI 中の SYS_CMD ハンドリング**: AVR64DD28 から音量変更 SYS_CMD が来た場合、現行の keyscan.c は Read のみのため無視される。対応するか
- **フォントロードのタイミング**: アプリ選択 UI のタイトル表示に日本語フォントが必要な場合、恵梨沙フォントロードを選択 UI の前に入れる必要があるか

### 5.3 Pattern 3: 外部通信モード（決定ボタン押下・GPIO2=HIGH）

```
boot_main()
  → 決定ボタン押下 → GPIO2=HIGH 確認
  → CART_READY HIGH（PCが準備完了を認識）
  → FRAM 0x08000〜0x0FFFF（SPI Flash 管理処理・32KB）を App Area にロード
  → ソフトウェアリセット → 管理プログラム起動
  → USB HID 経由で PC と SPI Flash 読み書き
```

**欠落候補・確認事項:**
- **管理プログラム終了後の処理**: 正常終了後に自動リセットして Pattern 1/2 に戻るか、PC 側から明示的にリセット指示を送るか
- **外部通信モードとブートローダアップデートの排他制御**: GPIO2=HIGH のときに上下キーも押されていた場合の優先順位

### 5.4 Pattern 4: ブートローダセルフアップデート（上下キー同時押し）

```
boot_main()
  → 上下キー同時押し検知
  → SPI Flash システム予約ブロックからアップデートプログラム（〜512B）を App Area に書き込み
  → ソフトウェアリセット → アップデートプログラム起動
  → CRC32 検証
  → __disable_irq()
  → Flash 書き換えルーチンを SRAM 上に展開・実行
  → 0x0000〜0x07FF を消去 → 新ブートローダで上書き
  → App Area（0x1E00〜0x3FFF）を消去
  → ソフトウェアリセット → 新ブートローダ起動
```

**欠落候補・確認事項:**
- **CRC32 ミスマッチ時のフォールバック**: 古いブートローダを保持したまま中断してリセットするか、エラー表示するか（現行仕様に未記述）
- **App Area 消去の必要性**: アップデート後に App Area を消去しているが、旧アプリの残存が問題になるケースはあるか

### 5.5 Pattern 5: LOCAL UPDI アップデート（★未実装・トリガー未定義）

```
（トリガー未定義）
  → 更新対象（AVR64DD28 or ATtiny404）の選択
  → SPI Flash からターゲット FW バイナリを読み込み
  → 対象ピン（PD0 or PD6）で UPDI bit-bang
  → 更新中の制約適用（FM 音源停止 / e-ink 描画停止）
  → 更新完了後に制約解除
  → 動作確認（UPDI リセット → 新 FW 起動確認）
```

**確認が必要な事項:**
- トリガー（boot 時特殊キー？システムメニュー？PC 外部通信モードのサブコマンド？）
- FW バイナリの格納場所（SPI Flash のどのブロック）
- 失敗時の対処
