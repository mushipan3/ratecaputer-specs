## 2. 3層アーキテクチャ概要

CAR-01（UIAPduino版）のソフトウェアは3層で構成される。

```
┌─────────────────────────────────────────┐
│  3層: アプリ（App Area 8KB）             │
│  開発者が実装。ゲーム・ツール・ノベル等    │
│  RcApi（1層）・2層ライブラリを呼び出す    │
├─────────────────────────────────────────┤
│  2層: 共通モジュール（SPI Flash上）       │
│  IAPコンテキストスイッチで呼び出す         │
│  セーブデータAPI・描画拡張ライブラリ等     │
│  ※コンテキストスイッチ中は音声が途絶える   │
├─────────────────────────────────────────┤
│  1層: 共通プログラム（内蔵Flash固定）     │
│  起動シーケンス・RcApi・IAP・SPIマネージャ │
│  アドレス固定（0x0800〜0x1DFF）          │
└─────────────────────────────────────────┘
```

| 層 | 提供形態 | 呼び出し方 | 用途 |
|---|---|---|---|
| **1層** | 内蔵Flash固定（0x0800〜0x1DFF） | RcApiテーブル経由で直接呼び出し | 起動・IAP・キースキャン・表示最小・リソースロード |
| **2層** | SPI Flash上（IAPで呼び出し） | iap_call()でロード後に呼び出し | 機能リッチな描画・セーブデータAPI・Arduboy互換レイヤー |
| **3層** | App Area（IAPで書き換え） | 直接実装 | ゲームロジック・オーディオ・日本語入力エンジン |

**オーディオの位置づけ：** コンテキストスイッチ中は音声が途絶えるため、オーディオ機能は3層（アプリブロック組み込み）とする。〜1KBを目標サイズとする。YMF825の初期化・音色設定はアプリ起動時の初期化ブロックで実施する。

## 3. 内蔵Flashレイアウト

CH32V003の内蔵Flash 16KBは全機種（TFT・OLED・e-ink）で統一レイアウトを採用する。

```
0x0000 ┌─────────────────────────┐
       │ UIAPduinoブートローダ   │ 2KB枠（0x0000〜0x07FF）
       │                         │ 実測1,892B・計算基準2,048B
0x0800 ├─────────────────────────┤ ← リンカORIGIN・LENGTH=5632
       │ ラテカ共通プログラム    │ 5.5KB枠（0x0800〜0x1DFF）
       │ UIAPduino2KB込み合計    │ 7.5KB
0x1E00 ├─────────────────────────┤
       │ 共通モジュール置き場    │ 512B（0x1E00〜0x1FFF）
       │ （開発者自由領域）      │ IAPによるApp Area書き換えで上書きされない
0x2000 ├─────────────────────────┤
       │ App Area（3層）         │ 8KB（0x2000〜0x3FFF）
0x3FFF └─────────────────────────┘
```

| 領域 | アドレス | サイズ | 書き換え手段 |
|---|---|---|---|
| UIAPduinoブートローダ | 0x0000〜0x07FF | 2KB枠 | セルフアップデートのみ |
| 共通プログラム（1層） | 0x0800〜0x1DFF | **5.5KB枠** | USB HID経由 |
| 共通モジュール置き場 | 0x1E00〜0x1FFF | **512B** | write_program.py等で書き込む |
| App Area（3層） | 0x2000〜0x3FFF | **8KB** | IAPで書き換え |

> **2026-07-15アドレス是正（Rev.0.4）**: 旧版は共通プログラム枠を0x0800〜0x1BFF
> （5KBにしかならず「5.5KB」表記と自己矛盾）、共通モジュール置き場を0x1C00〜、
> App Areaを0x1E00〜（8.5KBで「8KB」表記と矛盾）としていた。TFT版App Area拡大構想
> （10KB時代）の名残による誤りで、正しくは上表のとおり全領域が16KBへ過不足なく
> 整列する。実装・試験環境全域の是正はコミットeb13087（回帰全PASS）で完了済み。

**実測値（2026-07-15更新）：**
- 共通プログラム単体：**5,280B**（IAP可変サイズコンテキストスイッチPhase 2a+
  ブートローダー領域スワッププール+Phase 2b 4a/4b実装後）
- 5.5KB枠（5,632B）に対する余裕：**352B** ✅
- RcApiテーブル配置：**0x08A0**（割り込みベクタテーブル160B直後）
- 旧実測（参考）: 全機能実装直後5,140B・UIAPduino込み7,188B（Rev.0.1時点）

**CH32V003の3層ブートローダ構造：**

| 層 | 場所 | 書き換え手段 | 備考 |
|---|---|---|---|
| System Flash | 別物理領域 | 不可能 | WCH工場固定・UARTブートローダ |
| UIAPduinoブートローダ | 0x0000〜0x07FF | セルフアップデート機能のみ | rv003usbベース・USB HID実現 |
| 共通プログラム（1層） | 0x0800〜0x1DFF | USB HID経由 | 通常の開発サイクル |
| App Area（3層） | 0x2000〜0x3FFF | IAP（共通プログラムが担当） | SPI Flashから書き換え |

## 4. 起動シーケンス

```
【電源投入】
    ↓
UIAPduinoブートローダ起動（USB書き込み待機・タイムアウト後0x0800へジャンプ）
    ↓
boot_main()（共通プログラム起点）
    ↓
キースキャン処理を呼び出し
    ↓
    ├─ 上下キー同時押し → ブートローダセルフアップデートモードへ（§5.6参照）
    │
    ├─ 決定ボタン未押下
    │       ↓
    │   App Areaにアプリが存在するか確認
    │       ├─ 存在する → 字体スロット選択の読込 → App Areaに制御を移す
    │       └─ 存在しない → 決定ボタン押下時と同じフローへ
    │
    └─ 決定ボタン押下
            ↓
        200ms待機（キーボード側GPIO2セットアップの猶予）
        GPIO2確認 → HIGH: 外部通信モード（SPI Flash管理処理を起動）
                  → LOW:  アプリロード処理へ
            ↓
        FRAMの管理領域からアプリ一覧を読み込み
        TFT/e-inkにアプリタイトルリストを表示
        キースキャン: 上下で選択・決定で確定
            ↓
        RAM展開型IAPを呼び出し（選択した先頭ブロック番号を引数）
        SPI Flashからプログラムブロック（App Area 8KB）を焼く
        メタ情報領域（6KB）をFRAM作業領域に転送
            ↓
        ソフトウェアリセット

【再起動（アプリ起動フロー）】
    ↓
ブートローダ → boot_main()
    ↓
字体スロット選択をFRAM設定（1B）から読み込む（既定=slot0・範囲外は0へフォールバック）
← 日本語表示は最初から可能（フォントはSPI Flashから直読みするため展開待ちがない）
← Rev.0.5までは「フォントをSPI Flash→FRAMへ転送（約55KB・約18ms）」していたが、
   Rev.0.6で直読み化したため**この転送は廃止**（起動が約18ms短縮）
    ↓
決定ボタン未押下 → App Areaに制御を移す → アプリ起動
```

## 5. 1層：共通プログラム仕様

### 5.1 モジュール構成

| モジュール | 実測サイズ | 内容 |
|---|---|---|
| UIAPduinoブートローダ | 2KB | 起動プロセス呼び出し分岐追加版 |
| boot.c | — | アプリ選択UI・起動フロー分岐 |
| app_loader.c | 〜1KB | FRAMキャッシュからアプリ一覧取得・表示・選択 |
| spi_manager.c | 〜0.5KB | ハードウェアSPI直接制御・CS4系統切り替え |
| tft_oled.c または eink.c | 〜1KB / 〜3KB | 最小ドライバ・初期化シーケンス（機種別） |
| iap.c | 〜0.5KB | RAM展開型IAP・iap_run/call/return |
| keyscan.c | 〜1KB | I2C経由ジョイスティック入力読み取り |
| font_elysia.c | 〜0.2KB | 英数ビットマップフォント（余剰領域） |
| rc_api.c | — | RcApiテーブル（0x08A0固定配置） |
| **合計** | **5,140B（確定）** | |

### 5.2 RcApiテーブル（固定アドレスAPI）

RcApiは固定アドレス **0x08A0** に配置される12関数のAPIテーブル。アプリ（3層）はこのテーブルを通じて共通プログラムの機能を呼び出す。アドレスが固定のため、共通プログラムを更新してもアプリのバイナリを再コンパイルせずに利用できる。

**ディスプレイ非依存（機種共通）：**

```c
iap_run(uint32_t flash_addr)
    // アプリ切り替え（パターンB・戻らない）

iap_call(uint16_t callee_res_id, uint8_t catalog_idx, uint8_t call_type)
    // モジュール（サブプログラム）呼び出し（パターンA・戻る）
    // callee_res_id: 呼び出し先のリソースID（種別0x0）
    // catalog_idx: 呼び出し先アプリのカタログインデックス（0xFF=自アプリ=A-1）
    // call_type: IAP_CALL_INTERNAL=0 / IAP_CALL_EXTERNAL=1
    // 戻り値: IapCallStatus（4B・status/fram_free）
    //   status: 0=OK / 1=WARN_NEAR_FULL（継続可・FRAM使用量12KB超の予告）
    //           -1=ERR_SRAM_FULL / -2=ERR_FRAM_FULL
    //           -3=ERR_NOT_FOUND（リソース未登録） / -4=ERR_PLACEMENT（配置不能）
    //   エラー時（負値）はFlash書き換えなしで即時に呼び出し元へ戻る
    // ※2026-07-13改訂: flash_addr直指定→リソースID指定へ（可変サイズ
    //   コンテキストスイッチ設計）。旧caller_id引数は廃止（呼び出し元の
    //   同一性はIAP機構が保持する実行状態から取得）
    // ※2026-07-14追補（Rev.0.3）: 可変サイズ版の実装が完了し、本シグネチャが
    //   現行実装となった（単体試験でエンドツーエンド実証済み・実機確認は未了）。
    //   挙動の要点:
    //   - A-1（同一アプリ内）は呼び出し先が在席なら消去・書込なしの直接ジャンプ
    //     （ソフトリセットなし・高速パス）
    //   - 機構が呼び出し元の sp/ra/s0/s1/gp を保存・復元する。呼び出し元の
    //     静的変数（gp相対アクセス分を含む）とスタックは復帰後も保たれる
    //   - 成功時の戻り値は復帰ジャンプ経由でa0に設定される（通常の関数呼び出し
    //     と同じ感覚で戻り値チェックが書ける）
    //   - アプリ側の注意: カタログ申告サイズはFlashセル占有も決めるため、
    //     実バイナリより小さい申告は禁止（申告サイズ≥実バイナリ必須）

iap_return(void)
    // 呼び出し元に戻る

load_resource(uint16_t res_type_id, uint32_t fram_dest_addr)
    // SPI Flash→FRAM作業領域へリソースロード

keyscan_get(void)
    // ボタン状態取得（ビットマスク）

keyscan_wait(uint8_t mask)
    // 指定ボタン押下待機

keyscan_get_button(uint8_t button)
    // 特定ボタン確認
```

**ディスプレイ依存（機種ごとに実装が異なる）：**

```c
disp_init(void)          // 初期化
disp_fill(DispColor c)   // 全面塗りつぶし
disp_draw_string(...)    // 文字列描画（恵梨沙フォント・位置指定込み）
disp_set_window(...)     // 描画ウィンドウ指定
disp_write_pixel(...)    // 1ピクセル書き込み（→2層移管を検討）
```

**色定数（uint16_t統一）：**

```c
typedef uint16_t DispColor;
#define DISP_BLACK  0x0000U  // 全機種: 黒
#define DISP_WHITE  0xFFFFU  // 全機種: 白
#define DISP_RED    0xF800U  // TFT: 赤 / e-ink4色: 赤 / 白黒: 黒寄り
#define DISP_GREEN  0x07E0U  // TFT: 緑 / 白黒: 白寄り
#define DISP_BLUE   0x001FU  // TFT: 青 / 白黒: 黒寄り
```

**API公開方針：**

| カテゴリ | 公開先 | 理由 |
|---|---|---|
| RcApiテーブル（12関数） | 全アプリ向け | 機種非依存の標準API・固定アドレス0x08A0 |
| FRAM低レベルI/O（fram_write等） | 共通プログラム内部専用 | アプリによる誤書き込み・破壊を防ぐ |
| SPI Flash低レベルI/O（flash_read等） | 共通プログラム内部専用 | カタログ・フォント領域の保護 |
| セーブデータAPI | 2層ライブラリとして提供 | FRAM保護領域（0x02000〜0x05FFF）に限定 |

### 5.3 IAPパターン

CAR-01のIAPには3パターンがある。

| パターン | 名称 | 戻り | 用途 |
|---|---|---|---|
| B | ソフトリセット（1ブロック完結型） | 戻らない | ノベルゲーム・シナリオ連続再生 |
| A-1 | 同一アプリ内モジュール呼び出し | 戻る | 大規模アプリのモジュール分割 |
| A-2 | 別アプリ呼び出し | 戻る | アプリ間サービス呼び出し |

**所要時間（推定・CH32V003 @48MHz）：**

| フェーズ | 時間 |
|---|---|
| 内蔵SRAM 2KB → FRAM退避 | 0.7ms |
| SPI Flashからモジュール読み出し（8KB） | 5.5ms |
| 内蔵Flash消去（4セクタ） | **80ms**（ボトルネック） |
| 内蔵Flash書き込み（8KB） | **26ms** |
| ソフトリセット〜再起動 | 5ms |
| FRAMからSRAMイメージ復元 | 0.7ms |
| **合計（標準）** | **≈117ms** |
| **合計（最悪）** | **≈290ms** |

### 5.4 IAPコンテキストスイッチ（パターンA）

> **2026-07-14追補（Rev.0.3）**: 本節の固定2KB方式（ContextEntry 2,062B・最大7段）は
> **可変サイズ方式へ改訂され、実装完了・単体試験実証済み**となった。現行仕様の要点:
>
> - **ContextEntry v3**: 固定ヘッダ32B（restore_flag/call_type/呼び出し元識別・
>   sp/ra/s0/s1/**gp**・リソースID・sram_size）＋ 可変部（実際に使用中のSRAM分のみ・
>   64〜1,024B）＋ フッタ2B。SRAM 2KB全体ではなく申告サイズに応じた退避量となり、
>   1回の退避・復元が最大30倍高速化される
> - **ネスト段数の固定上限（7段）は廃止**: FRAMコンテキストスタック16KB枠（§7）の
>   残量による動的チェックに置き換え。小型モジュールなら約167段まで積める計算で、
>   実運用でFRAMが律速することはまず無い。残量逼迫はiap_call戻り値の
>   WARN_NEAR_FULL/ERR_FRAM_FULLで通知される（§5.2）
> - **A-1の高速パス**: 呼び出し先がApp Area内に在席していれば消去・書込・リセット
>   なしの直接ジャンプで起動する
> - gpの保存・復元はRev.0.3で追加（呼び出し元の静的変数アクセスを完全に保つため）
>
> 以下の固定2KB方式の記述は旧設計の参考として残す。

**コンテキストスタック構造（旧・固定2KB方式）：**

```c
typedef struct {
    uint8_t  restore_flag;       // 1=有効
    uint8_t  module_id;          // 呼び出し元モジュールID
    uint8_t  call_type;          // IAP_CALL_INTERNAL=0 / IAP_CALL_EXTERNAL=1
    uint8_t  pad;
    uint32_t sp;                 // 呼び出し元スタックポインタ
    uint32_t ra;                 // 呼び出し元戻りアドレス
    uint32_t caller_flash_addr;  // 呼び出し元ブロックのSPI Flashアドレス
    uint8_t  sram_image[2048];   // 内蔵SRAM 2KBスナップショット
} ContextEntry;  // 計2,062B
```

**スタック配置（FRAM作業領域先頭）：**

| 項目 | サイズ | 内容 |
|---|---|---|
| スタック深さカウンタ | 1B | 現在のネスト段数 |
| エラーコード・予備 | 15B | デバッグ情報等 |
| コンテキスト[0]〜[6] | 2,062B × 7 = 14,434B | 各段のSRAMイメージ+復帰情報 |
| **合計** | **約14.5KB** | |

**最大ネスト段数：7段**（8段目は16,480Bとなり16KBブロックを超過するため不可）

**IAP引数・戻り値エリア（FRAM管理領域）：**

> **Rev.0.5（2026-07-17）で改訂:** メタ情報領域内（+0x1680〜+0x177F・各64B）から**FRAM管理領域へ移設**し、各256Bへ拡大した。旧配置ではA-2（別アプリ呼び出し）の引数受け渡しが**原理的に成立していなかった**（下記）。

| 領域 | FRAMアドレス | サイズ | 用途 |
|---|---|---|---|
| IAP A-1引数（INTERNAL） | 0x1A900 | 256B | 同一アプリ内モジュール呼び出し引数 |
| IAP A-1戻り値（INTERNAL） | 0x1AA00 | 256B | 同上・戻り値 |
| IAP A-2引数（EXTERNAL） | 0x1AB00 | 256B | 別アプリ呼び出し引数 |
| IAP A-2戻り値（EXTERNAL） | 0x1AC00 | 256B | 同上・戻り値 |

実装の正は `iap.h` の `FRAM_IAP_A1_ARG` / `FRAM_IAP_A1_RET` / `FRAM_IAP_A2_ARG` / `FRAM_IAP_A2_RET`（サイズは `FRAM_IAP_ARG_SIZE`）。

**移設の理由**: メタ情報領域はアプリのFlashメタブロックの**キャッシュ**である。A-2では機構が、呼び出し時に呼び出し先アプリのメタ8KBを、復帰時に呼び出し元アプリのメタ8KBを、それぞれ**Flash原本から再転送する**（呼び出し先のリソースディレクトリを引くために必要で、A-2に本質的な動作）。旧配置の4領域はいずれもこの8KBの内側にあったため、**A-2引数は呼び出し時に、A-2戻り値は復帰時に、機構自身が塗り潰していた**。A-1（メタ入替なし）は旧配置でも往復内では動作したが、「引数を書く→A-2呼び出し→A-1呼び出し」の順に並ぶと間のA-2がメタを原本へ戻すため**A-1引数が無言で失われる**（機構は引数エリアを参照しないため検出不能）。安全性がコードの並び順という規律だけに依存する状態を避け、4領域とも移設して**メタ情報領域を純粋なFlashキャッシュとした**。

**アプリ側の規約**: 引数・戻り値の受け渡しには必ず上記の管理領域を使うこと。**メタ情報領域はアプリが書き込む場所ではない**。引数は呼び出しの直前に書き、呼び出し先は入場直後に読む。継続して必要な値は自分のZone C（機構が退避・復元する）へ写すこと。機構はこの領域を参照しないため、内容の保護も検証も行わない。

検証: IT-IAP-03（A-1）／IT-IAP-04（A-2・引数往復＋呼び出し元メタの復元）で実証済み（`CAR-01_test_result_phase2`）。

### 5.5 SPI Flash管理処理

FRAMの固定領域（0x08000〜0x0FFFF・32KB）に格納する独立したプログラム。boot_main()がGPIO2=HIGHを検出した場合にIAP経由で内蔵Flashに書き込まれ実行される（外部通信モード）。

**役割：**

| 役割 | 内容 |
|---|---|
| PCとのデータ交換 | USB HID経由でSPI Flashの読み書き消去を行う |
| カタログ管理 | SPI Flash上のアプリカタログを更新する |
| FRAMキャッシュ更新 | カタログ変更後にFRAMの管理領域キャッシュを更新する |

**HIDレポートフォーマット（確定）：**
64B固定（USB Full Speed物理制約）：`cmd(1B) / seq(1B) / addr(4B) / length(2B) / data(56B)`

### 5.6 ブートローダセルフアップデート

boot_main()起動時に**上下キー同時押し**で呼び出す。WCH-LinkEを不要とするための仕組み。

**SPI Flash格納場所：** システム予約ブロック内1ブロック先頭4KB

```
0x000 ┌──────────────────────┐
      │ アップデートプログラム │ 〜512B（SRAM展開型）
0x200 ├──────────────────────┤
      │ 新ブートローダバイナリ │ 2KB（0x0000〜0x07FFに書く内容）
0xA00 ├──────────────────────┤
      │ チェックサム（CRC32） │ 4B
0xFFF └──────────────────────┘
```

**動作フロー：**

```
上下キー同時押し検出
    ↓ SPI Flashからアップデートプログラム（〜512B）をApp Area（0x2000〜）にIAPで書き込む
    ↓ ソフトウェアリセット → アップデートプログラムが起動
    ↓ CRC32検証 → 新ブートローダをSRAMに読み込む
    ↓ __disable_irq()
    ↓ Flash書き換えルーチンをSRAM上に展開・実行
    ↓ 0x0000〜0x07FFを消去 → 新ブートローダで上書き
    ↓ App Area（0x2000〜0x3FFF）を消去
    ↓ ソフトウェアリセット → 新ブートローダ起動
```

## 7. FRAMレイアウト

1チップ構成。グレードで容量のみ異なり、アドレス構造は共通。

**設計原則（2026-07-13再配置）：** 擬似マルチタスク（複数アプリ/タスクの共存）を見据え、FRAMを「タスク数に依存しない**不変部**」（先頭に固める）と「タスクごとに1組必要な**タスク比例部**」（後方にスロットとして積む）に分離する。タスク数を増やしても不変部には一切手が入らない。

> **Rev.0.6（2026-07-18）で再配置**: **フォントをFRAMからSPI Flash直読みへ移行**したため先頭の64KB枠が不要になり、SPI Flash管理処理〜管理領域を繰り上げ、跡地を**予備バッファ**（今後のシステム仕様変更に備えて確保・他用途へ転用しない）とした。
>
> **移行の理由**: FRAMとSPI Flashは**同一SPIバス・同一24MHz・同一READ方式**であり、共通プログラムの実装でも両者は速度設定を共有している。当初「FRAMはSRAM相当の速さ」という前提でフォントを展開していたが、その前提は成立しない。グリフ読み出しのコストはCS選択先が変わるだけで、FRAM展開は**64KB消費＋起動時55KB転送（約18ms）**を払うだけだった。フォント原本は元からSPI Flash 0x008000 にあり、データは移動していない。
>
> **配置の意図**: `32+8+8+64 = 112KB = 0x1C000` となり、**セーブデータ（ユーザーの永続データ）とタスクスロット領域が1バイトも動かない**。また予備バッファが「**伸びうるもの**」＝管理領域（カタログキャッシュはアプリ数が58を超えれば増える）とセーブデータに挟まれ、両方向から伸びられる。

```
FRAM（256KB or 512KB）
0x00000 ┌──────────────────────┐
        │ SPI Flash管理処理    │ 32KB（固定）※最も不変・最大の領域を先頭に
0x08000 ├──────────────────────┤
        │ 共通プログラム領域   │ 8KB（自己復元用バックアップ）
0x0A000 ├──────────────────────┤
        │ 管理領域             │ 8KB
        │                      │ ├ カタログキャッシュ: 26B×58 = 1,508B
        │                      │ ├ App Area配置状態表: 512B枠（8B×32+LRUカウンタ+予備）
        │                      │ ├ プール在席テーブル: 16B（0x0A800）
        │                      │ ├ 字体スロット選択: 1B（0x0A8F0・既定slot0）
        │                      │ ├ IAP引数・戻り値エリア: 1KB（0x0A900〜0x0ACFF・256B×4）
        │                      │ └ デバイス共通予備: 約4.75KB
0x0C000 ├──────────────────────┤
        │ 予備バッファ         │ 64KB（旧フォント展開枠・システム仕様変更に備えて確保）
0x1C000 ├──────────────────────┤
        │ セーブデータ         │ 16KB
0x20000 ╞══════════════════════╡ ここからタスクスロット領域
        │ タスクスロット#0     │ スロット内オフセット固定:
        │  +0x0000 メタ情報コピー 8KB
        │  +0x2000 コンテキストスタック 16KB（可変長ContextEntry・動的容量チェック）
        │  +0x6000 アプリ作業領域（スロット割当分）
        │ （タスクスロット#1〜: 擬似マルチタスク導入時に追加）
        │ スタンダード版: 0x20000〜0x3FFFF = 128KB
        │ プレミアム版:   0x20000〜0x7FFFF = 384KB
```

**FRAMアドレス正式値（Rev.0.6・2026-07-18再配置・シングルタスク=スロット#0のみの縮退形）：**

| 領域 | 開始アドレス | サイズ | 根拠 |
|---|---|---|---|
| SPI Flash管理処理 | **0x00000** | 32KB | 不変部。最も不変・最大の領域を先頭に |
| 共通プログラムバックアップ | **0x08000** | 8KB | 不変部（自己復元用） |
| 管理領域（カタログキャッシュ・配置状態表・プール在席・字体選択・IAP引数） | **0x0A000** | 8KB | 不変部（配置状態表はApp Area 32セルの状態で有界）。約3.25KB使用・約4.75KB空き |
| **予備バッファ** | **0x0C000** | **64KB** | 旧フォント展開枠。今後のシステム仕様変更に備えて確保（他用途へ転用しない）。**伸びうるもの**（管理領域・セーブデータ）に挟まれ両方向から伸びられる |
| セーブデータ | 0x1C000 | 16KB | 不変部（永続データ・タスク数非依存）。**Rev.0.5から不動** |

※ **フォント展開領域は廃止**（Rev.0.6）。フォントはSPI Flash 0x008000 から**直読み**する（§8 SPI Flashレイアウト・96KB×4スロット）。
| メタ情報コピー（FRAM_META_BASE） | 0x20000 | 8KB | タスクスロット#0 +0x0000 |
| コンテキストスタック（CTX_STACK_BASE） | 0x22000 | 16KB | タスクスロット#0 +0x2000。可変長ContextEntry・WARN 12KB/ERR 16KBの動的チェック |
| アプリ作業領域 | 0x26000 | 残り全て | タスクスロット#0 +0x6000（スタンダード: 約104KB／プレミアム: 約360KB） |

**旧レイアウト（2026-06-24版）からの主な変更：** ①不変部/タスク比例部の分離原則を導入 ②コンテキストスタックを固定7段14,464Bから可変長・16KB枠に変更（可変サイズコンテキストスイッチ設計による。詳細は開発リポジトリの`iap_context_switch_variable_design.md`） ③App Area配置状態表を管理領域内に新設 ④メタ情報コピーとアプリ作業領域を明確に分離（旧版は`FRAM_META_BASE`=0x23880を「アプリ自由作業領域」と記載しており、メタ情報コピー8KBとの区別が曖昧だった） ⑤実装移行は可変サイズコンテキストスイッチの実装と同時に1回で行う（現行ファームは旧レイアウトで動作中）。

**UIAPduino交換方針：** UIAPduino本体（約290円）はFlash書き換え上限（約10,000回）に達したら交換する。FRAMとSPI Flashにすべてのデータが保全されているため、挿し替えだけで自動復元される（共通プログラムをFRAM 0x06000から自己IAPで復元）。
