## 3. App Areaの制約

**App Area：0x2000〜0x3FFF（8KB）・全機種統一**

> **2026-07-17是正**: 旧記述は `0x1E00〜0x3FFF（8KB）` としていたが、この範囲は8.5KBで「8KB」表記と自己矛盾していた（TFT版App Area拡大構想＝10KB時代の名残による誤り）。正しい内蔵Flashレイアウトは **ブートローダ 0x0000〜0x07FF／共通プログラム 0x0800〜0x1DFF（5.5KB）／共通モジュール置き場 0x1E00〜0x1FFF（512B）／App Area 0x2000〜0x3FFF（8KB）** で、全領域が16KBへ過不足なく整列する。正本は `CAR-01_common_program_spec` §3（Rev.0.4で是正済み）。実装・試験環境全域の是正は完了済み（回帰全PASS）。

アプリ本体コードはこの8KB以内に収める。IAPにより任意のタイミングで内容が切り替わる。

```
App Area（8KB）
├── アプリ本体コード（ゲームロジック・インタプリタ等）
├── オーディオ再生機能（〜1KB目標・YMF825制御）
└── （IAPコンテキストスイッチを使う場合）アセンブリスタブ
```

**メタ情報領域（6KB・App Areaの直後）：**
SPI Flash上のアプリブロックに付随するメタデータ領域。コンバータが自動生成する。

| オフセット | サイズ | 内容 |
|---|---|---|
| 0x0000 | 4KB | アプリ内ブロックディレクトリ#0（512エントリ×8B・プログラム専用） |
| 0x1000 | 32B | リソース種別開始アドレス表（type_start[16]） |
| 0x1020 | 約1KB | FM音色定義（48音色・種別0x5・★2026-08-14 に 0xF から移動） |
| 0x1400 | 512B | シナリオ継続情報（SCN_PTR・フラグ群・パターンBソフトリセット用） |
| 0x1600 | 128B | アプリメタ情報（タイトル・作者・バージョン・ビルド日時） |
| 0x1680 | 256B | **予約（未使用）** — 旧IAP引数/戻り値エリア。2026-07-17にFRAM管理領域へ移設 |
| 0x1780 | 128B | 予備 |

> ⚠ **メタ情報領域はアプリが書き込む場所ではありません。** この領域はアプリのFlashブロック後半をFRAMへ転送した**キャッシュ**であり、別アプリ呼び出し（A-2）の呼び出し／復帰のたびに**Flash原本から再ロードされます**。ここへ書いた内容は保存されません。

### IAP引数・戻り値エリア（FRAM管理領域）

**2026-07-17に、メタ情報領域内（+0x1680〜+0x177F・各64B）から下記へ移設しました（各256B）。**

| 領域 | FRAMアドレス | サイズ | 用途 |
|---|---|---|---|
| IAP A-1引数（INTERNAL） | 0x1A900 | 256B | 同一アプリ内モジュール呼び出しの引数 |
| IAP A-1戻り値（INTERNAL） | 0x1AA00 | 256B | 同上・戻り値 |
| IAP A-2引数（EXTERNAL） | 0x1AB00 | 256B | 別アプリ（公開サービス）呼び出しの引数 |
| IAP A-2戻り値（EXTERNAL） | 0x1AC00 | 256B | 同上・戻り値 |

共通プログラム側の定数は `iap.h` の `FRAM_IAP_A1_ARG` / `FRAM_IAP_A1_RET` / `FRAM_IAP_A2_ARG` / `FRAM_IAP_A2_RET`（サイズは `FRAM_IAP_ARG_SIZE`）です。

**なぜ移設したか**: 旧配置は4領域ともメタ情報領域の内側にありました。A-2では共通プログラムが呼び出し時に呼び出し先アプリのメタ8KBを、復帰時に呼び出し元アプリのメタ8KBを、それぞれFlash原本から再転送します（呼び出し先のリソースディレクトリを引くために必要な動作）。このため**A-2引数は呼び出し時に、A-2戻り値は復帰時に、機構自身が塗り潰していました**＝A-2の引数受け渡しは成立していませんでした。A-1（メタ入替なし）は旧配置でも動作しましたが、「引数を書く → A-2呼び出し → A-1呼び出し」の順に並ぶと間のA-2がメタを原本へ戻すため**A-1引数が無言で失われる**（機構は引数エリアを参照しないため検出できません）。このため4領域とも移設しました。

**使い方の規約**:

- 引数は**呼び出しの直前に書き、呼び出し先は入場直後に読む**こと。継続して必要な値は自分のZone C（静的変数・スタック）へ写すこと。Zone Cはコンテキストスイッチで退避・復元されます
- 戻り値は**`iap_return()` の直前に書く**こと
- 引数・戻り値エリアは全アプリ共通の固定領域です。共通プログラムは一切参照しないため、**内容の保護も検証も行いません**

## 4. RcApiの使い方

共通プログラム（1層）の機能はすべてRcApiテーブル（固定アドレス **0x08A0**）経由で呼び出す。

```c
// rc_api.h（アプリが#includeする）
#include "rc_api.h"

// 使用例
void my_app_main(void) {
    // ディスプレイ初期化
    RcApi.disp_init();

    // 全面塗りつぶし
    RcApi.disp_fill(DISP_BLACK);

    // 文字列描画
    RcApi.disp_draw_string(10, 20, "Hello!", DISP_WHITE);

    // ボタン待機
    RcApi.keyscan_wait(JOY_CENTER);

    // アプリ切り替え（戻らない）
    RcApi.iap_run(NEXT_BLOCK_ADDR);
}
```

**ディスプレイ独立性：** disp_*関数はTFT・e-ink・OLED全機種で同一APIを呼び出す。機種ごとの差異は共通プログラム内部で吸収される。

## 5. リソース管理

### リソースエントリ構造体（8バイト固定）

```c
typedef struct {
    uint16_t res_type_id;   // [15:12]=種別(4bit) [11:0]=ID(12bit)
    uint16_t block_cell;    // [15:4]=ブロックID(12bit) [3:0]=セルID(4bit)
    uint8_t  size[3];       // サイズ（バイト・最大16MB）
    uint8_t  reserved;
} ResourceEntry;
```

### リソース種別

| 種別値 | 内容 |
|---|---|
| 0x0 | プログラム（IAPで別モジュールをロード） |
| 0x1 | 画像 |
| 0x2 | 音声（BGM） |
| 0x3 | 音声（効果音） |
| 0x4 | 音声（ボイス） |
| **0x5** | **FM音色定義**（★2026-08-14 に 0xF から移動） |
| **0x6** | **シナリオテキスト**（★2026-08-14 に 0x5 から移動） |
| **0x7** | **スクリプトプログラム**（★2026-08-14 新設。ゲームエンジンのスクリプト等） |
| 0x8〜0xD | 未定義（予備・6枠） |
| **0xE** | **パッチテーブル**（PC側コンバータが自動生成・★2026-08-14 に 0x6 から移動） |
| **0xF** | **ディレクトリ拡張ブロック**（★2026-08-14 に 0xE から移動） |

> ★**2026-08-14 に種別番号を並べ替えた**（正本＝`cartridge_master` §1.8）。
> 0x0〜0x7 ＝開発者が用意するコンテンツ／0xE〜0xF ＝コンバータが自動生成する管理データ。

### リソースのロード

```c
// SPI Flash上のリソースをFRAMへロード
// res_type_id: [15:12]=種別 [11:0]=ID
// area       : 転送先の領域ID（RcApi が番地を決める。アプリは生アドレスを持たない）
//                LOADRES_AREA_WORK(0) = 共有作業領域 64KB
//                LOADRES_AREA_FB  (1) = 合成バッファ 86,400B（全画面画像・FBPS対象）
// off        : その領域の先頭からのオフセット（バイト）
// 戻り値     : 0=成功 / 1=領域ID不正 / 2=リソース不在 / 3=範囲外
uint8_t rc = RcApi.load_resource(0x1001, LOADRES_AREA_WORK, 0x8000);  // 画像ID=1
```

> ★**2026-08-14 変更**: 旧版はアプリが FRAM の生アドレスを渡す2引数だったが、
> **境界検査が一切なく**、範囲外を指定するとスロット領域やシステム領域を破壊できた。
> 領域IDとオフセットに改め、範囲検査を共通プログラム側で行う。
> FRAM はメモリマップされていないため、アプリが生アドレスを持つ利点はもともと無い。

**重ね合わせはアプリの責務。** 共通プログラムはロード・転送まで担い合成には関与しない。

### アプリ規模の目安

| 規模 | 対象グレード | ディレクトリブロック数 |
|---|---|---|
| シンプル（小規模ゲーム） | スタンダード | 1ブロック（〜512エントリ） |
| 中規模ゲーム | スタンダード〜プレミアム | 1〜2ブロック |
| 大規模（Fate規模・声なし） | プレミアム | 2〜3ブロック（1,000〜1,500リソース） |
| 超大規模（Fate規模・声あり） | プレミアム | 数十ブロック（数千〜1万リソース） |

## 5.5 セーブ指針（★2026-07-30 追加・擬似マルチタスク導入に伴う）

### 区切りで自発的にセーブすること

**利用者のセーブ操作を待つだけでなく、ステージ切り替えなどアプリにとって自然な区切りで
自発的にセーブしてください。**

**理由**: 擬似マルチタスクでは同時に起動できるユーザーアプリ数に上限（7）があり、
上限に達した状態で新しいアプリを起動したい利用者は、**既存のアプリをどれか一つ終了**
させる必要があります。この**終了はセーブを伴いません（未セーブのデータは失われます）**。

これは意図的な決定です。「未セーブだから一度アプリへ戻る」という導線を設けると、
たとえばシューティングの最中に戻り、ゲームを一瞬再開してセーブしてから終了する、
という不自然な操作になります。**そのような場合はステージの最初へ戻る**という粒度を
受け入れる方針としました。

> **但し書き**: 将来「セーブのためにアプリへ戻るか選ばせる」UI が追加される可能性は
> あります（D基板側の UI の問題であり、アプリ側の機構には影響しません）。ただし
> **本ガイドラインの推奨（区切りでの自発セーブ）は、その場合も有効です。**

### 何を失ってよいか設計しておくこと

終了で失われるのは**セーブしていない進行状態**です。逆に言えば、

- **セーブ済みの地点まで巻き戻る**ことは利用者に許容される
- ∴ **巻き戻り粒度＝セーブ間隔**をアプリ側で決められる

シューティング/アクションならステージ開始時、ノベルゲームなら章や選択肢の直後、
といった単位が目安です。

### サスペンド（切替）とは別物

| | 終了 | サスペンド（アプリ切替） |
|---|---|---|
| 状態 | **破棄**（未セーブぶんは失われる） | **保持**（機構が自動退避・復帰） |
| 契機 | 利用者がスロットを空けるために選ぶ | 利用者が別アプリへ切り替える |
| アプリ側の対応 | 区切りでセーブしておく | **不要**（機構が面倒を見る） |

**切替では何もしなくて構いません。**本指針が必要なのは「終了」のときだけです。

## 6. IAPパターンの使い分け

### パターンB：ソフトリセット（推奨・シンプル）

戻らない。状態をFRAMに明示保存して次ブロックで参照する。ノベルゲーム・シナリオ連続再生に適する。

```c
// 状態をFRAMのシナリオ継続情報に保存
fram_write(SCN_PTR_ADDR, &next_addr, sizeof(next_addr));

// 次ブロックに切り替え（戻らない）
RcApi.iap_run(next_block_flash_addr);
```

### パターンA：コンテキストスイッチ（上級・複雑）

戻る。SRAMイメージをFRAMに退避して復元する。大規模アプリのモジュール分割に適する。

```c
// 別モジュールを呼び出す（戻る）
RcApi.iap_call(module_flash_addr, MODULE_ID, IAP_CALL_INTERNAL);

// モジュール側でiap_return()を呼ぶと元のブロックに戻る
```

**所要時間：** 約117〜290ms。FEPのような頻繁な呼び出しには不向き。場面転換・シーン切り替えなど「イベント」として呼ぶ用途が適切。

### パターンA を使うアプリの規約（5件）

コンテキストスイッチ（パターンA）は可変長のコンテキスト退避・復元と、App Area へのモジュール動的配置を伴う。安全に使うため以下5件の規約がある。多くは**PC側カタログ生成ツール**がビルド時に自動保証・fail-closed 検査するが、開発者（特に公開サービス提供側）が意識すべき項目も含む。

| # | 規約 | 誰が保証するか | 違反時に起きること |
|---|---|---|---|
| 1 | **申告サイズ ≥ 実バイナリサイズ** | PC側ツールが保証・検査 | アロケータが自領域を空きと誤認し、実行中モジュールのセルを別モジュールに割り当てて**無言で破壊**する |
| 2 | **A-2 公開サービスはステートレス**（呼び出し間で状態を保持しない） | 開発者（サービス提供側） | A-2は呼び出し／復帰のたびにメタ領域をFlash原本から再ロードするため、状態が消える |
| 3 | **App Area を使い切る可能性のあるアプリは本体(main)にもパッチテーブルを登録する** | PC側ツール（要件・チェック検討中） | 本体が追い出され、復帰時の sticky 再ロードで `find_resource(PATCH\|本体)` が引けず**無言でハング**（安全網なし） |
| 4 | **引数・戻り値は FRAM 管理領域の4定数を使う。メタ領域には書かない** | 開発者（→ §3「IAP引数・戻り値エリア」参照） | A-2で機構がメタ領域を再ロードし、書いた内容が消える |
| 5 | **ld の `__global_pointer$` は絶対値 `0x200007FC`（SECTIONS の外で定義）** | PC側ツールが ELF シンボル値を検査。プロジェクト提供のテンプレート ld を使えば自動達成 | 機構の静的変数アクセス（gp相対）がアプリの gp でずれ、Zone C を**無言で破壊**する |

- **規約3の補足**: 本体は通常 cell0・delta=0 で動くためパッチテーブルを必要としないが、App Area が溢れて本体が追い出され再ロードされる瞬間にだけ要求される（`iap_call_impl` の採番順により本体が最初の追い出し犠牲者になりやすい）。パッチ内容は delta=0 の実質 no-op でよいが、**テーブルの存在自体**が必要。
- 各規約の背景・経緯の詳細は共通プログラム設計書 `iap_context_switch_variable_design.md` §8.7、規約5は `gp_abi_design.md` を参照。

## 7. オーディオ実装方針

**オーディオ機能は3層（アプリブロック組み込み）。** コンテキストスイッチ中は音声が途絶えるため1層・2層には含めない。

```
App Area（8KB）内:
├── アプリ本体コード
└── オーディオ再生機能（〜1KB目標）
    ├── YMF825 SPI送信ラッパー（CS_YMF=PD2）
    ├── FM音源再生コマンド
    └── ADPCM/PWM再生（AUDIO_IN経由・UIAPduino PC3）
```

**YMF825初期化：** アプリ起動時に初期化ブロック（IAPで呼び出し）でYMF825の初期化・音色設定を完了させる。アプリ本体からはレジスタ書き込みのみ行う（再初期化不要）。

**音量制御：** YMF825マスターボリュームレジスタ（0x19）をUIAPduino経由でAVR64DD28（ジョイスティック操作）からソフトウェア制御する。詳細は `features_system_menu_20260725.md` §4参照。

## 8. 日本語表示

恵梨沙フォント（6877文字・各8B）は **SPI Flash（0x008000）に常駐し、グリフを都度 SPI Flash から直読み**する（`common_program_spec` Rev.0.6 で FRAM 展開を廃止。FRAM と SPI Flash は同一SPIバス・同一24MHz・同一READ方式のため展開しても速度は変わらず、起動時の約18ms転送と64KBのFRAM消費が消えた）。アプリ開発者はフォントのロードもアドレス計算も書く必要はなく、描画関数にインデックスを渡すだけでよい。

```c
// 恵梨沙フォントindex配列をそのまま渡す。SPI Flash直読みは共通プログラム内部で行われる
// （アプリ側でフォントアドレスを計算する必要はない）
RcApi.disp_draw_string_elysia(x, y, elysia_index_array, len, color);
```

**タイトル文字列：** CatalogEntryのtitleフィールドは恵梨沙フォントindexの配列（uint16_t×8文字）。UTF-8やShift-JISではなくインデックスで格納する。PC側ビルドツールが変換を担当する（PENDING #1）。

## 9. ノベルゲーム開発

バイトコード方式のノベルゲームインタプリタをApp Areaに組み込む構成。

**参考実装（Fate/stay night規模・声なし）：**

```
App Area（8KB）:
├── ノベルゲームインタプリタ本体
└── オーディオ再生機能（〜1KB）

SPI Flash上:
├── シナリオデータ（バイトコード列）
├── 背景画像・CG
├── BGM（YMF825 VGMバイナリ）
└── 効果音（ADPCM）
```

**ブロック切り替え（パターンB）：**

```
(1) インタプリタがCMD_BLOCK_NEXT [SPI_FLASH_ADDR]命令を検知
(2) FRAMのシナリオ継続情報に以下を書き込む
    ・次ブロックのSPI Flashアドレス（SCN_PTR）
    ・継続に必要な環境状態（背景ID・BGM ID等）
    ・長寿命フラグ群
(3) iap_run()で次のバイトコードブロックをApp Areaに上書き
(4) ソフトウェアリセット
(5) 再起動後のインタプリタがFRAMのSCN_PTRを参照して続きから再開
```

**シナリオフォーマット：** バイトコード方式で詳細は未決定（PENDING #2）。GB Studio・NScripter・吉里吉里KAGを参考として設計する。

## 10. 開発フロー

### PC側ビルドツール（将来整備・PENDING）

```
アプリソースコード（C言語）
    ↓ riscv32-unknown-elf-gcc
アプリバイナリ（8KB）

シナリオ・画像・音声素材
    ↓ PC側コンバータ（Python）
リソースバイナリ群
    ↓ PC側パッケージャ
SPI Flash書き込みイメージ（.bin）
    ↓ USB HID（write_program.py等）
SPI Flash（W25Q128JVSIM）
```

**PC側ツールが行う fail-closed 検査（パターンA 規約・§6参照）**: カタログ生成時に以下を機械検査し、違反はビルドエラーとする（実行時には安全網が無く無言破壊・ハングに至るため、ビルド時点で止める）。
- 規約1: 各モジュールの**申告サイズ ≥ 実バイナリサイズ**
- 規約5: ELF の **`__global_pointer$` == 0x200007FC**
- 規約3: 本体にパッチテーブルが登録されているか（App Area を使い切り得るアプリ向け・実装検討中）
