## 2. 概要

CH32V303（144MHz・FPU内蔵・DAC×2ch・SRAM最大64KB）を「専用オーディオコプロセッサ」として動作させる。UIAPduino（CH32V003・FPU非搭載・48MHz・SRAM2KB）では実現困難な処理を全て引き受け、UIAPduinoはゲームロジックとUIに専念できる構造とする。

**本ファームウェアが担う機能の全体像：**

| カテゴリ | 機能 |
|---|---|
| FM音源制御 | YMF825-EZ×2をSPI制御・L/R独立発音 |
| PSG音源生成 | ソフトウェア矩形波合成・ステレオ（L/R独立） |
| ADPCM再生 | W25Q128JVから読み出し・ソフトウェアミキシング多重再生 |
| リズム音源 | 固定打楽器バンクからの専用スロット再生 |
| DSP/エフェクト | ソフトリミッタ・フィルタ・ディレイ等（段階的実装） |
| 演算オフロード | レイキャスティング計算・浮動小数点演算（FPU活用） |
| 通信 | UIAPduinoとのUART通信（コマンド受信・ADPCM転送受け取り） |

## 3. アーキテクチャ

### 3.1 コプロセッサ方式の採用

UIAPduinoがYMF825を直接SPI制御していた旧B基板方式（案B相当）に対し、CH32V303を間に挟む「コプロセッサ方式（案A）」を採用した。

| 検討した方式 | 内容 | 採否 |
|---|---|---|
| 案A（採用） | CH32V303が音源制御を一手に引き受け、UIAPduinoはUART経由で高レベルコマンドのみ送信 | ◯採用 |
| 案B | UIAPduinoがYMF825を直接制御し、CH32V303はPSG/ADPCM生成専任 | ✕（FM側にDSP処理が及ばない） |

**採用理由：** UIAPduinoの負荷を増やさず、FM/PSG/ADPCMの同期を一元管理できる。SPI生信号がCH32V303に閉じ込められ、外部エッジパッド数の削減にも寄与した。

なおCH32V303が「UIAPduinoに対するUARTスレーブ的役割」と「YMF825×2・W25Q128JVに対するSPIマスター」を同時に持つことは、別ペリフェラル・別ピンのため不整合は生じない（センサーハブIC等で一般的な構成）。

### 3.2 スケジューリング設計

オーディオ生成（タイマー割り込み駆動）と演算オフロード（レイキャスティング等）の同居を、割り込み優先度で整理する。「手隙の時にバッチ処理」ではなく、以下の優先度構造で両立させる。

```
【最優先・割り込み】PSG/DAC生成（タイマー駆動・DMAバッファ補充）
  → 短時間・周期的・絶対に遅延させない

【メインループ・低優先度】レイキャスティング等の演算・UARTコマンド処理
  → リクエストが来たら即座に実行開始するが、
    オーディオ割り込みが発生すればその都度中断・再開する
```

これにより、ゲーム側から見れば「毎フレーム必須の低レイテンシ要求（33ms以内）」を満たしつつ、オーディオ側から見れば「最優先割り込みにより確実に保護される」という、2つの異なる時間軸の要求を両立する。手続き的コンテンツ生成等の遅延許容ジョブは別途真のバッチ/キュー処理（優先度を下げて空き時間に処理）が適する。

## 4. FM音源制御

YMF825-EZ×2をSPIバス（SCK/MOSI/MISO共有・CS_YMF_L/CS_YMF_R独立）で制御する。左右チャンネルをそれぞれ独立した音色・音量・パンで発音できる真のステレオ構成とする。

旧spec §7.1記載の「SCK/CS/RST共有・MOSIのみ分岐」方式では両チップに同一コマンドが同時着弾するため独立ステレオ制御ができない（二重化モノラルに留まる）。CS分離（GPIO+1本のコスト）により真のステレオを実現する。

YMF825のSPI通信はMode 0（CPOL=0・CPHA=0）・最大10MHz。UIAPduino→CH32V303で音色番号・音量・パン等の高レベルコマンドを受け取り、CH32V303がYMF825レジスタへの書き込みシーケンスに展開する。

---

## 5. PSG音源生成

PSGはハードウェアチップを搭載せず、CH32V303のソフトウェア矩形波合成で実装する。チャンネル数はハードウェア制約に縛られず設計上の取り決めとして決定できる。

**ベンチマーク（PC-9801-86/YM2608）との比較：** YM2608のSSG部は3チャンネルが内部でミキシングされてからモノラルで出力される仕様だった。本設計はL/R独立のステレオPSGとして実装するため、この点は86ボードを機能面で上回る。

ソフトウェア実装のため、ハードウェアPSGにはない拡張が可能である（ADSRエンベロープの実装・チャンネル数の柔軟な設定等）。

**PENDING：** チャンネル数（L/R各3ch相当か、それ以上か）、ADSRエンベロープ等の拡張機能の実装範囲（PENDING #1）。

## 6. サンプル再生エンジン

### 6.1 ミキシングエンジン構成

W25Q128JV（16MB）に格納したADPCMサンプルを読み出し、デジタルミキシングしてCH32V303内蔵DAC（L/R各1ch）へ出力する。

```
CH32V303内 デジタルミキサー:
  メロディックADPCMスロット × N（掛け声・SE等、ゲームごと動的）
  リズムスロット × 4〜8（固定打楽器バンクから・専用予約）
  PSG × L/Rチャンネル数
  ↓ 全てデジタル加算
  DAC_OUT_L / DAC_OUT_R
```

PC-9801-86の「86PCM」は16bit1ch専用回路をソフトウェアミキシングで多重再生していた。本設計のADPCMエンジンも同じ発想を採用し、当時のエンジニアが採った解決策を現代のMCUパワーで再現する。

### 6.2 リズム音源スロット

YM2608の「リズム音源」（内蔵ROM6種類の打楽器サンプルを、FM/PSGの発音リソースを消費せず専用チャンネルで鳴らせる仕組み）に相当する機能をソフトウェアミキシングエンジン内に設ける。リズムスロットを別腹で確保することで「掛け声を再生中でも太鼓の音が確実に割り込んで鳴る」という利点を再現する。

**サンプルバンク分割案：** W25Q128JV内に「固定打楽器バンク」領域（例：先頭64KB程度を予約・全ゲーム共通）と「ゲームごと動的ADPCM」領域を分け、YM2608のROM打楽器という発想を外部フラッシュ内の専用パーティションとして模倣する。

**トリガー方式の選択肢（PENDING #2）：**

| 方式 | 内容 | 適性 |
|---|---|---|
| ホスト主導 | UIAPduinoがビートに合わせてUART経由で軽量コマンド（1byte程度）を都度送信 | ゲームロジック側でリズムを完全制御したい場合 |
| CH32V303内蔵シーケンサ | パターンテーブル（例：16ステップ×4トラック）をレベルロード時に1回転送し、CH32V303が自律再生 | UART通信量を削減・ジッタの影響を受けにくい |

**PENDING #2：** 固定/動的バンクの容量配分、内蔵シーケンサの具体的なフォーマット、トリガーから発音までのレイテンシ（DACバッファサイズとのトレードオフ）の実機検証。

### 6.3 サンプルデータのストレージ方針（PCM格納確定）

W25Q128JV（16MB）に格納するサンプルデータのフォーマットは**PCMのまま格納（無変換）**とする。

**ADPCM変換を不採用とした経緯：** 当初「PC側でADPCM（4bit）に事前変換してから格納する」方式を検討した。しかし以下の理由で不採用とした。

- **音質劣化が不可避：** 16bit PCM→4bit ADPCM変換は1/4に圧縮できる代わりに量子化ノイズが乗る。.xmサンプルをそのまま再現するという目的に反する
- **ADPCMはランダムシークが困難：** ADPCM圧縮データは先頭から逐次デコードしないと任意位置にシークできない。.xm再生ではアルペジオやポルタメントで高速にサンプル再生位置を変更する必要があり、多チャンネル同時にこれが走ると処理が破綻するリスクがある
- **PCMのまま格納しても容量は十分：** .xmのサンプルデータ総量は一般的に数MB程度であり、16MBに対して余裕がある。ADPCMにして4倍の容量を稼ぐ必要性がない
- **デコード処理が不要になりCPUサイクルを節約できる：** CH32V303はシーケンス演算・エフェクト処理・FMコマンド生成を並行して行うため、ADPCMデコードの負荷を省けることは有益

なおADPCMは「カスタムサウンド領域での容量節約手段」としてオプション的に保持する（W25Q128JVに余剰がある限り掛け声等もPCMで格納する方針）。

**W25Q128JVのパーティション構成（案）：**

```
W25Q128JV（16MB）:
  ├─ 固定打楽器バンク（先頭64KB予約・PCM・全ゲーム共通）
  ├─ .xmサンプルデータ領域（PCM 8bit/16bit・ゲームごと動的書き換え）
  └─ カスタムサウンド領域（掛け声等・容量に余裕があればPCM優先・不足時はADPCMも選択肢）
```



## 7. DSP・エフェクト処理

FM（YMF825→アナログ出力）とPSG/ADPCM（CH32V303 DAC出力）はアナログ段で抵抗ミキシングするが、PSG+ADPCM同士はCH32V303内部でデジタル加算した後にエフェクト処理を適用できる。

**計算予算の目安：** サンプリングレート22kHzで処理する場合、1サンプルあたり144MHz÷22kHz≒約6,500クロックが使える計算で、簡単なフィルタ処理には十分な余裕がある（§8の演算オフロードタスクと共存させる場合は要再計算）。

| エフェクト | 内容 | 優先度 |
|---|---|---|
| ソフトリミッタ/クリッパー | FM+PSG+ADPCM加算後のクリッピング防止 | 高（ほぼ必須） |
| 簡易フィルタ（LPF/HPF） | チャンネル毎・マスターバス毎のトーン調整 | 中 |
| ディレイ/エコー | フィードバック付き単純遅延 | 中 |
| 簡易リバーブ | Schroeder型（コムフィルタ+オールパス） | 低〜中 |
| コーラス/フランジャー | LFO変調ディレイ | 低 |

**ベンチマーク（PC-9801-73）との比較：** 73ボードはDSP（μPD6380）によるエフェクト機能を搭載していたが、文献によれば「実際にはこの機能を実用的に用いたソフトウェアは無かったようである」とされ、事実上活用されなかった。本プロジェクトはファームウェアを100%自前で書くため、「ハードはあるがソフトが追いつかない」という失敗パターンに陥らない。実装すれば確実に使われる、という点が「73超え」の本質的な意味となる。

## 8. 演算コプロセッサ機能

### 8.1 浮動小数点演算オフロード

UIAPduino（RV32EC・FPU非搭載）は三角関数・平方根・除算がソフトウェア実装となり非常に重い。CH32V303（FPU内蔵）にUART経由でsin/cos/sqrt/atan2等の計算を依頼し結果を受け取ることで、ゲームロジック側の物理演算・回転・拡大縮小を現実的な速度で実現する。

### 8.2 レイキャスティング計算オフロード

CH32V303のFPUで列ごとの壁距離をDDA法で計算し、結果（距離配列）のみをUIAPduinoへ返す方式により、Wolfenstein 3D方式の疑似3D表現を実現する。

**データフロー：**

```
UIAPduino → CH32V303: プレイヤー位置(x,y)・向き(angle)
CH32V303:  各列についてDDA法でレイキャスティング
           → 壁距離算出（FPU多用）→ 魚眼補正
CH32V303 → UIAPduino: 列ごとの距離配列(+壁テクスチャID)
UIAPduino: 受け取った距離配列を元に縦線を描画するだけ
```

**帯域試算：** 240列・距離8bit量子化で1フレーム240バイト。30fpsなら7.2KB/s程度で、UART（1Mbps想定・実効100KB/s前後）に対して十分余裕がある。CH32V303側の計算（144MHz・FPU）はDDA法240本でもサブミリ秒〜数ミリ秒で収まる見込みで、フレーム予算（33ms）に対して余白が大きい。

**マップデータ：** 迷路グリッド（例：32×32マス・1KB程度）はレベル開始時に1回だけCH32V303のSRAMへ転送し常駐させる方式とし、毎フレームの送信は不要とする。

**段階的拡張：** まず壁だけの単色シェーディング版を実装し、テクスチャマッピング・スプライト描画（敵キャラ等の距離ソート）は次のステップとする（PENDING #3）。

## 9. .xmトラッカー再生エンジン実装方針

### 9.1 .xmフォーマットの構造と再生エンジンに必要な処理

.xm（Extended Module）はOpenMPT等のトラッカーで使われるサンプラー形式である。内蔵音源チップを直接鳴らす形式ではなく、短い音声サンプル（波形データ）をファイル内に取り込み、トラッカーのエフェクトコマンドで制御して演奏する。

再生エンジンが担う処理は以下の5層から構成される。

```
1. ファイルパーサー    : ヘッダ・パターン・サンプルデータを解析
2. パターンシーケンサー: 行(row)を時間軸で進め、各チャンネルのノート・
                          エフェクトコマンドを発行
3. チャンネルステート管理: 各チャンネルのピッチ・音量・パン・エンベロープ・
                            エフェクト状態を保持（tick毎に更新）
4. エフェクトコマンド処理: アルペジオ(0xx)・ポルタメント(3xx)・ビブラート等
5. サンプルミキサー    : 各チャンネルのサンプルを補間しながら合成しDAC出力
```

**CH32V303での実現性：** 既存のハードウェア設計（W25Q128JV＋CH32V303 DAC＋YMF825）は.xm再生エンジンが必要とするリソース構成と完全に合致している。UIAPduinoは「曲データをCH32V303に転送して再生開始を指示するだけ」というさらにシンプルな役割になり、設計思想的にもむしろ望ましい方向である。

### 9.2 データ配置設計

| ストレージ | 用途 | 理由 |
|---|---|---|
| W25Q128JV（16MB） | .xmサンプルデータ（PCM格納）・打楽器バンク・カスタムサウンド | 容量優先。§6.3参照 |
| CH32V303 Flash（256KB） | 再生エンジン本体コード＋パターンデータ | 高速アクセス必要 |
| CH32V303 SRAM（64KB） | チャンネルステート・先読みバッファ・ミキサー作業領域 | 毎tick書き換えるためSRAMが必須 |

**Flash容量の試算：**

| 用途 | 推定サイズ |
|---|---|
| 再生エンジン本体コード（libxm移植ベース） | 約20〜40KB |
| パターンデータ（Motorway級1曲分） | 約30〜80KB |
| インストゥルメント定義・マッピングテーブル | 約5〜10KB |
| システム全体（ベアメタル・RTOS不使用） | 約10〜20KB |
| **合計** | **約65〜150KB** |

256KBのFlashに対して余裕がある見込みだが、曲数が増えてFlashを圧迫する場合はパターンデータをW25Q128JVの別パーティションに逃がす設計を検討する。

### 9.3 サンプルデータのPCM格納方針（ADPCM変換不採用の経緯）

§6.3に詳述。要点はADPCM変換を行わず.xm原データのPCM（8bit/16bit）をそのままW25Q128JVに格納することで、音質劣化の排除・ランダムシーク容易化・デコード処理の省略を同時に実現する。

### 9.4 アルペジオ・ポルタメントへの対処

.xm再生で最も処理負荷が高い箇所はアルペジオ（0xxコマンド・1tick毎に音程を高速切り替え）とポルタメント（音程の連続変化）である。これらはサンプルの再生位置・ピッチを毎tick変更することで実現される。

**デコード済みバッファ方式を採用する：** 各チャンネルのサンプルをW25Q128JVから1tick分（数百バイト）だけ先読みしてSRAMのチャンネルバッファに展開し、SRAM上でピッチ変換（補間）・ミキシングを行う。PCM格納であれば任意バイト位置から直接読み出せるため、ADPCMのような逐次デコード問題が発生しない。

SRAM 64KBをチャンネル数で割ると1chあたり2KB程度となり、短いサンプルのループ再生には十分である。

### 9.5 FM音源チャンネルへの積極的振り分け

.xmのサンプルチャンネルを全てW25Q128JV→DACで再生する必要はない。以下の方針でFM音源（YMF825）とサンプル再生を役割分担させる。

| チャンネル種別 | 割り当て先 | 理由 |
|---|---|---|
| シンセリード・ベース（FMシンセ系・アルペジオ多用） | YMF825（FM合成） | W25Q128JVへのランダムアクセス不要・FMの方が音質的に優位 |
| 生楽器サンプル（スラップベース・エレピ・ドラム） | W25Q128JV→DAC | 波形の再現性が重要 |
| 矩形波・PSG系 | CH32V303ソフトウェアPSG | サンプル消費なし |

.xmのチャンネルをどの音源に割り当てるかは変換ツール（PC側）またはインストゥルメントマッピングテーブルで事前に定義する。

### 9.6 移植候補エンジン（libxm）

ゼロから書く必要はなく、組み込み向けの実績がある既存エンジンを移植する。

| エンジン | 言語 | 特徴 | CH32V303への適性 |
|---|---|---|---|
| **libxm** | C | 軽量・.xmに特化・MIT・組み込み意識の設計 | **◎ 最有力**。SRAM使用量が少なく出力バックエンドが差し替え可能 |
| MilkyPlay | C++ | 高互換性・重め | △ C++依存が多くポーティングコスト高 |

libxmは「ここにPCMサンプルを出力する」という出力バックエンド部分を差し替えられる設計になっており、「FM音源系チャンネル→YMF825へSPIコマンド変換、サンプル系チャンネル→PCMデコードしてDAC出力」という分岐処理に置き換えることでCH32V303+YMF825構成に対応できる。

**PENDING #9：** libxmの実際のSRAM/Flash使用量・CH32V303（RISC-V RV32）へのコンパイル検証。

### 9.7 FRAMの位置づけ（努力項目）

.xm再生エンジン実装に際しFRAMの有効性を検討した結果を以下に示す。

| 用途 | FRAM有利か | 判断理由 |
|---|---|---|
| サンプルデータ格納 | ✕ | 容量（MB85RS4MT 512KB vs W25Q128JV 16MB）でFlashが圧倒 |
| チャンネルステート管理 | ✕ | SRAM（毎クロック読み書き）の方が圧倒的に高速 |
| パターンデータ格納 | △ | Flash消耗を防ぎ・曲数増加時のFlash容量不足を緩和できる |

パターンデータ用途では、FRAMへの格納はFlashの書き換えサイクル寿命（10万回）を消費せずに曲の差し替えができるという副次的メリットもある。ただし現時点では1曲のパターンデータ（30〜80KB想定）に対してFlash（256KB）は十分余裕があるため、FRAMは**基板面積に余裕がある場合の努力項目**として位置づける。量産版でKiCad実配置の結果面積余裕が確認できた場合にのみ搭載を検討する。

## 10. 通信プロトコル

### 10.1 UARTフレーム仕様（旧§9.1）

点対点（UIAPduino⇔CH32V303）のシンプルなフレーム構成を想定する。詳細はソフトウェア設計時に別途確定する。

```
[開始バイト][コマンドID][長さ][ペイロード...][CRC]
```

リアルタイム性が必要な軽量コマンド（音色変更・リズムトリガー等）と、ゲームロード時の大容量ADPCM転送が同一ストリームに混在するため、コマンドIDで種別を判別する設計とする（PENDING #4）。

**物理接続（確定）：**

```
UIAPduino PD5(TX) ──→ CH32V303 PA14(UART3_RX2/SWCLK兼用)
UIAPduino PD6(RX) ←── CH32V303 PA13(UART3_TX2/SWDIO兼用)
```

CH32V303のPA13/PA14はSWDIO/SWCLKと同一ピンに多重化されており、リセット直後はSWDが有効、ファームウェア起動後にUART3に切り替えて通信を開始する。WCH-LinkEを接続して「Connect under reset」すればいつでもファームウェア書き換えが可能。UIAPduino側のPD5/PD6は新B基板の設計変更（YMF825がCH32V303配下へ移行することでIRQ_NがUIAPduinoに来なくなりPD6が解放、PD5のRST_DISPは起動時一回限りのため常時UART使用に支障なし）により常時UART通信として使用できる。

### 10.2 コマンド分類

| カテゴリ | 内容 | レイテンシ要件 |
|---|---|---|
| FM音色制御 | YMF825音色番号・音量・パン設定 | 低レイテンシ |
| PSG制御 | 周波数・音量・エンベロープ設定 | 低レイテンシ |
| リズムトリガー | 固定打楽器バンクの発音指示 | 低レイテンシ |
| .xm再生制御 | 再生開始・停止・曲切り替え | 低レイテンシ |
| データ一括転送 | ゲームロード時のサンプルデータ・パターンデータ転送 | スループット優先 |
| 演算オフロード要求 | レイキャスティング等（§8参照） | フレーム予算内（中レイテンシ） |

### 10.3 データ一括転送（ゲームロード時）

.xmサンプルデータ（PCM）・パターンデータの合計はNORフラッシュ典型速度（約80KB/s）で数十秒〜1分程度で書き込み可能であり実用上ボトルネックにならない。UIAPduino側の許容ライン（ゲーム全体最大8MB超を約80KB/sで2分弱）との比較でも十分小さい規模である。通信路（UART+DMA、200KB/s超見込み）がNORフラッシュ書き込み速度の律速より速い点も確認済み。

## 11. クロック・リセット設計

### 11.1 クロック

外付け8MHz水晶（HSE→PLLで144MHz等に逓倍）を採用する。内蔵HSI使用は不採用とした。

**採用理由：** 内蔵HSIの精度（推定±1〜3%）はYMF825（12.288MHz水晶ロック）との同時発音時に聴感上明確な音程ズレ（±1%で約17セント、±3%で約50セント級）を生む。YMF825に特殊な12.288MHz水晶を採用して音質を作り込んだ経緯があり、CH32V303側だけ精度を妥協するのは一貫性に欠けるため、外付け水晶を採用した。

### 11.2 リセット

CH32V303のリセットはシステムNRST（UIAPduino基準）と共有する。UIAPduinoのアプリ切り替え機構は`iap_call()`/`iap_return()`（ソフトウェアコンテキストスイッチ・NRSTなし）と`iap_run()`（Flash書き換え後に実リセット）の2系統があり、NRSTが発生するのは`iap_run()`実行時（ユーザーが別アプリ/ゲームを起動する瞬間）のみである。CH32V303のリセットをこれに連動させることで「再起動後も前のアプリの音楽が鳴り続ける」事象を防止する。メニュー内の軽量なコンテキストスイッチではNRSTが発生しないため、音声再生が不要に途切れることもない。

## 13. ベンチマーク比較：PC-9801-86/73

### 13.1 PC-9801-86ボード（YM2608/OPNA）仕様概要

PC-9801-86（1993年発売・定価2.5万円）はYM2608（OPNA）を搭載し、PC-9800シリーズの事実上の標準サウンドボードとなった。DSPによるエフェクト機能は86ボードではなく上位機種PC-9801-73（定価9.8万円）の機能であり、86ボードはコストダウンのためこれを省略した廉価版である。

| 機能 | YM2608仕様 |
|---|---|
| FM音源 | 6ch・4オペレータ |
| SSG（PSG） | 3ch・モノラルミックス後出力（左右別パン不可） |
| リズム音源 | 内蔵ROM6種類の打楽器サンプル・専用チャンネルでステレオ再生可 |
| ADPCM | 4bit・1ch |
| 86PCM（86ボード独自） | 16bit・1ch、ソフトウェアミキシングで多重再生 |
| DSPエフェクト | 73ボードのみ（μPD6380）、実用化したソフトはほぼ無かった |

### 13.2 機能比較表

| 機能 | PC-9801-86 | 本設計 |
|---|---|---|
| FM音源 | 6ch・モノラル内部合成後ステレオ | YMF825×2・**真のステレオ独立制御** |
| PSG | 3ch・モノラルミックス | CH32V303ソフトウェア生成・**真のステレオ** |
| リズム音源 | 専用チャンネル・固定ROM | ソフトウェアミキシング内の専用スロット（§6.2） |
| PCM/サンプル再生 | ソフトウェアミキシングで多重再生 | 同じ発想をW25Q128JV+CH32V303で再現。PCM原音のまま格納し音質劣化なし |
| DSPエフェクト | 73ボードのみ・実用化せず | 自前ファームウェアのため実装すれば確実に使われる |
| .xmトラッカー再生 | 対応なし | libxm移植ベースで対応（§9参照） |

「73超え」とは当時のハードウェア限界を超えるという意味ではなく、**当時のソフトウェアエコシステムの限界（DSPはあったが誰も使わなかった）を超える**という意味で捉える。実装優先順位はソフトリミッタ（必須に近い）→簡易フィルタ→ディレイ/リバーブの順（§7参照）。
