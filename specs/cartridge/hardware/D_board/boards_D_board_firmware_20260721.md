## 1. 概要

本書はD基板搭載AVR64DD28のファームウェア仕様を定める。AVR64DD28はUIAPduino（CH32V003）のI2Cスレーブとして動作し、ジョイスティック入力・OLED描画・スリープ管理を担う。日本語入力システムおよびシステムメニューを含むシステム機能全般との協調動作の詳細は `CAR-01_japanese_input_20260717.md` および `features_system_menu_20260725.md` を参照。

---

## 2. 動作モード

| モード | 条件 | 動作 |
|---|---|---|
| RAWデータモード | 通常時 | ジョイスティック状態を1バイトビットフィールドでI2C Readに即答 |
| **システムメニューモード** | **ジョイスティックセンター長押し（約1秒）検知時** | **OLEDにシステムメニューUI表示・操作結果をSYS_CMDでUIAPduinoへ通知** |
| 日本語入力モード | UIAPduinoから開始通知を受信中 | ひらがな入力UI・OLED候補表示・ユーザ確定操作を全担当 |
| スリープ | UIAPduinoからスリープ指示を受信 | OLED表示オフ・定期スリープサイクル |

**モード排他制御：** 日本語入力モード中はシステムメニューモードへの遷移を禁止する（逆も同様）。AVR64DD28側でモード状態フラグを管理する。

---

## 3. I2Cスレーブ動作

UIAPduino（CH32V003）をマスターとする共通I2Cバス上でスレーブとして動作する。

| コマンド種別 | 方向 | 内容 |
|---|---|---|
| Read（RAWモード） | AVR64DD28→UIAPduino | ジョイスティック状態1バイト（bit7=0） |
| **Write/Read（システムコマンド）** | **AVR64DD28→UIAPduino** | **SYS_CMDバイト（bit7=1）：メニュー開閉・音量変更等。詳細はfeatures_system_menu_20260725.md参照** |
| Write（モード通知） | UIAPduino→AVR64DD28 | 日本語入力モード開始・終了・スリープ指示 |
| Write（バッテリー残量） | UIAPduino→AVR64DD28 | UIAPduinoがATtiny202から取得した残量値を転送 |

I2Cスレーブアドレス：TBD（PENDING #1 / `boards/D_board/hardware.md` 参照）

## 4. ジョイスティック入力処理

SKRHAAE010はデジタルスイッチのためADC不要。ポーリングで読み取る。

> 注: 下記コードのポート/ピン（`PORTA`・`PINn_bm`）は旧ATtiny1604割当に基づく**暫定**であり、AVR64DD28の物理ピン割当が
> 確定（HW仕様書 §4.2 PENDING #7・ユーザー決定）した時点で対応するポート/ビットへ更新する。ロジック（5入力・LOW=押下）は不変。

```c
uint8_t joystick_read(void) {
    uint8_t state = 0;
    if (!(PORTA.IN & PIN5_bm)) state |= JOY_UP;
    if (!(PORTA.IN & PIN6_bm)) state |= JOY_DOWN;
    if (!(PORTA.IN & PIN4_bm)) state |= JOY_LEFT;
    if (!(PORTA.IN & PIN3_bm)) state |= JOY_RIGHT;
    if (!(PORTA.IN & PIN7_bm)) state |= JOY_CENTER;
    return state;
}
```

**チャタリング除去：** 同一状態が連続2回（約10ms間隔）確認された時点で確定。

## 5. OLED描画

CH1115（I2Cアドレス0x3C）への描画はAVR64DD28が単独で担当する。UIAPduinoはOLEDに直接書き込まない。

**4階調表示**: CH1115は物理的に2値だが、AVR64DD28が4階調に対応する複数プレーンを**タイマ割込で高速にI2C送出する時間的
ディザリング**で4階調（2ビット）を再現する。フォントは主基板TFTと同一の2ビット4階調規格（HW仕様書 §4.4／§4.5・8ドット/12ドット
2サイズをローカルFlashに保持）。AVR64DD28はDMA非搭載のため、プレーン送出はタイマ割込＋ポーリングで組む（8KB SRAMにプレーンバッファを確保）。

### 5.1 動作モード別表示内容

| モード | OLED表示内容 |
|---|---|
| 日本語入力モード | 確定文字列・変換対象ひらがな・候補文字列群・バッテリー残量 |
| 通常モード | バッテリー残量＋スクリーンセーバー等の自由演出 |
| スリープ | OLED表示オフ |

### 5.2 バッテリーデータの取得フロー

AVR64DD28はバッテリー残量データをUIAPduino経由で受け取る。ATtiny202に直接アクセスしない。

```
UIAPduino → ATtiny202へReadリクエスト（定期ポーリング）
         ← 残量値1バイトを受信
UIAPduino → AVR64DD28へWrite（残量値を転送）
AVR64DD28 → 次回OLED描画時にバッテリー表示に反映
```

## 6. スリープ制御

```
[通常時]
AVR64DD28: 定期スリープ（数秒おき）
            ウェイクアップ → バッテリー表示更新 → スリープ

[日本語入力モード開始通知受信時]
AVR64DD28: スリープ禁止・フルスピード動作
            ジョイスティック入力監視・OLED描画・候補表示

[日本語入力モード終了通知受信時]
AVR64DD28: 通常時スリープサイクルへ復帰
```

## 7. メモリマップ

> ATtiny1604（16KB Flash / 1KB SRAM）からAVR64DD28（**64KB Flash / 8KB SRAM**）への移行に伴い再構成した。
> **具体アドレスは暫定**（ファーム実装時に確定・物理ピン割当PENDING #7と併せて詰める）。

| 領域 | サイズ（目安） | 内容 |
|---|---|---|
| ローカルフォント（2ビット4階調・2サイズ） | 約14.2KB | 8ドット16B/字＋12ドット36B/字・入力サブセット約280字×2サイズ（HW仕様書§4.5参照）。旧2KB・256文字1ビットから拡大 |
| プログラム領域 | 十数KB | I2C制御・ジョイスティック・OLED描画・**時間的ディザリング制御**・日本語入力UI・ウェアレベリング等 |
| 候補データ動的バッファ | 8KB程度 | 64B/ページ単位・自己書き換え（ウェアレベリングで分散） |
| 予備／将来拡張 | 残り | 64KB化で確保した余裕 |
| 内蔵EEPROM | 256B（AVR64DD28） | ウェアレベリングカウンタ等 |
| 内蔵SRAM | 8KB | UI操作・通信ワークエリア・**ディザリング用プレーンバッファ**（DMA非搭載のため割込＋ポーリングで送出） |

## 8. フラッシュ寿命試算

候補データバッファ（8KB・128ページ）への書き込みを完全巡回ラウンドロビンで分散。

| 想定使用頻度 | 推定寿命 |
|---|---|
| 1日20回変換（ヘビーユーズ） | 約22年 |
| EEPROMの同時消耗 | フラッシュ寿命時点でEEPROM定格の10%のみ消費 |
| チップ交換コスト | AVR64DD28（ATtiny1604より高価だが数百円級）・PCBA実装。候補バッファのウェアレベリングは64KB化で更に余裕 |

## 8.5 【要件・2026-08-07 追加】主基板の異常時にエラーコードを保持し復帰を誘導する

**状態: 要件として起票。設計・実装は未着手。** 主基板側の対応方式は検討中で未確定。

### 背景

主基板（UIAPduino）には `for(;;)` による fail-closed 停止が**38箇所**ある。
実機では独立ウォッチドッグ（IWDG・約8秒）が働くため、停止すると**自動的に再起動**する。
このとき主基板は SRAM を失い、原因を自分で覚えていられない。

一方 **D基板は主基板と一緒にはリセットされない**（電源は A基板供給・主基板からのリセット線を
設けない要件＝ハード仕様 §6.1）。∴ **D基板が異常の記憶を担える。**

### 要件

| # | 内容 |
|---|---|
| 1 | 主基板から I2C で受け取った**エラーコード（`REG_ALERT`）を保持する**。主基板がリセットしても失わないこと |
| 2 | コードに応じた**メッセージを OLED に表示**し、利用者の確認操作（OK）を待つ |
| 3 | 確認後、主基板の起動シーケンスに対して**キー入力を返す**ことで、主基板をアプリ選択画面へ誘導する（「同時押し」相当の入力を合成する） |
| 4 | 誘導が完了したらエラーコードを消去し、通常のキー入力に戻る |

### なぜ D基板側でやるのか

主基板の 1層 FLASH は **5632B の枠に対し現在 6524B（+892B 超過）** で、余地が無い。
主基板側で異常フラグを FRAM に永続化し起動時に読む方式だと、その分の実装が主基板に載る。
**D基板に状態を持たせれば、主基板側の追加はエラーコードの割り当てと入力分岐だけで済む。**

### 未確定事項

- エラーコードの体系（主基板側の `ALERT_*` は現在14種。停止38箇所への割り当ては未実施）
- 「同時押し」に何を使うか（主基板側の受け口とセットで決める）
- 表示メッセージの文言・コード対応表
